# produtos-imgs — Mupa Brain

API Flask de gestão de produtos/imagens para o app de consulta de preço da Mupa (`mplayer`). Roda na porta **5050**. Painel admin em `/configuracoes`.

## Tema escuro por padrão, com toggle pra claro

Pedido do usuário. `<html>` já nasce com `data-theme="dark"` (renderizado assim pelo servidor — evita flash de tema claro antes do JS rodar). Botão no topbar (`#btn-theme-toggle`, ícone lua/sol) alterna `data-theme` entre `"dark"`/`"light"` e persiste em `localStorage` (`mupa_painel_tema`); sem preferência salva, sempre abre escuro.

Implementado quase inteiramente via CSS custom properties: `html[data-theme="dark"] { --bg: ...; --card: ...; --border: ...; --text: ...; --muted: ...; --accent: ...; ... }` redefine os mesmos tokens que o `:root` já usa em claro — como o resto do CSS já era escrito em cima de `var(--bg)`/`var(--card)`/etc. (não cores literais), a troca de tema se propaga sozinha pro resto do painel sem precisar duplicar regras. Alguns lugares tinham cor **literal** hardcoded em vez de variável (`background:#fff` em inputs/botões/menu-toggle, `background:#f8fafc` no hover de botão secundário, `background:#fafbff` em 4 cards aninhados) — trocados por `var(--card)`/`var(--hover)`/`var(--bg)` pra também respeitarem o tema. A barra lateral (`--sidebar-*`) não precisou de bloco novo — já era escura nos dois temas.

**Não perseguido nesta leva** (aceito como inconsistência menor, não um bug): badges de status gerados via JS com cor pastel literal (ex. verde/vermelho claro dos badges "Encontrado"/"Não encontrado" no Histórico, âmbar do badge de tentativas) continuam com o mesmo hex em ambos os temas — ainda legíveis no escuro (fundo pastel + texto escuro), só não foram re-otimizados pixel a pixel pro tema escuro.

## Aba Histórico: painel de detalhes lateral (clicar no produto)

Pedido do usuário: clicar num produto da lista (qualquer filtro — agrupado "não encontrados" ou log bruto "todos"/"encontrados") abre um painel de detalhes na coluna direita, igual ao que já existia na Consulta Rápida. Em vez de generalizar o painel único da Consulta Rápida (`#detail-panel`/`openDetailModal`, fortemente acoplado a `loadConsulta`/`consultaPage`/`ultimoConsultaData`), criei um painel **paralelo e independente** pro Histórico (`#hist-detail-panel`/`openHistDetailPanel`, ids prefixados `hist-detail-*`) — mesmo HTML/CSS (`.consulta-layout`/`.consulta-detail-col`/`.detail-panel`/`.detail-modal-*`/`.detail-field`, todos genéricos o bastante pra reaproveitar), mesmas 3 rotas de backend (Buscar imagem, Gerar arte, Enviar/Trocar imagem), mas atualizando `loadHistorico(historicoPage)`/`removerLinhaHistorico` no lugar de `loadConsulta`. Evita acoplar os dois painéis e reduz risco de regressão na Consulta Rápida, ao custo de ~130 linhas de JS duplicadas (aceitável — mesmo padrão que `loadHistorico`/`loadConsulta` já coexistindo como implementações paralelas).

A aba Histórico ganhou o mesmo tratamento de layout largo que a Consulta Rápida (`$('#content')?.classList.toggle('wide', tab === 'consulta' || tab === 'historico')`).

`removerLinhaHistorico(codbar)` (já existia, das ideias 1-5) só encontra e remove `<tr data-codbar>` na vista **agrupada** — na vista de log bruto não há esse atributo no `<tr>` (só nos `<td>`, pra abrir o painel), então chamar a função ali é um no-op seguro. Corrigido um bug real encontrado ao ligar o painel de detalhes na vista de log: a função decrementava o contador "N registros" mesmo quando não achava/removia linha nenhuma — agora só decrementa se `row` existir.

**Pegadinha de teste, não bug**: `GET /produto/<ean>` (usado tanto pela Consulta Rápida quanto por este painel novo) monta a resposta com uma sugestão via Gemini (`gemini-2.5-flash-lite`) **síncrona** — a chamada inteira leva uns 15-25s. Ao testar/depurar esse painel, esperar tempo suficiente antes de checar o resultado (já aconteceu de eu achar, num primeiro momento, que o clique não funcionava — só estava sendo verificado cedo demais).

## Botão "Buscar com IA": busca de imagem na internet via Gemini (grounding com Google Search)

Pedido do usuário: um botão que usa IA pra procurar a foto do produto na internet e mostrar uma **lista de opções dentro do próprio painel** (sem sair do sistema/navegar pra outra página) — o usuário escolhe uma pra virar a foto do produto. Complementa o "Buscar imagem" que já existia (local → Bing → Google → Zaffari, automático, salva direto sem perguntar nada) — este aqui é o caminho "eu quero ver as opções e escolher", útil quando a busca automática falha ou traz a imagem errada.

Botão `#detail-btn-buscar-ia` / `#hist-detail-btn-buscar-ia`, presente nos dois painéis de detalhes (Consulta Rápida e Histórico), ao lado do "Buscar imagem" de sempre.

**Trocado de OpenAI pra Gemini no meio da implementação**: a primeira versão usava a Responses API da OpenAI (`web_search_preview`, via `requests` puro — o SDK `openai` desta máquina está na 0.27.0, API pré-1.0, sem suporte a isso). Funcionou tecnicamente, mas a chave da OpenAI configurada no painel estava **sem crédito** (`insufficient_quota`, HTTP 429 — confirmado chamando a API direto). O usuário pediu pra usar o Gemini em vez disso, que já é o provedor de IA principal do sistema (arte publicitária + sugestão de nome) com uma chave configurada e ativa. `_buscar_imagens_gemini_web` usa o mesmo padrão de client já usado em `gerar_termos_sugestao_ia`/`gerar_textos_arte_ia` (`genai.Client(vertexai=True, api_key=...)`), com o modelo `gemini-2.5-flash` e a tool `google_search` (`genai_types.Tool(google_search=genai_types.GoogleSearch())`) habilitada pra busca em tempo real (grounding) — diferente das outras chamadas Gemini do sistema, que são só geração sem acesso à internet.

**Fluxo, em duas rotas separadas** (buscar e definir são dois passos distintos — dá pro usuário ver as opções antes de decidir, em vez de a primeira encontrada já ser salva automaticamente como o "Buscar imagem" de sempre faz):
1. `POST /admin/buscar-imagem-ia/<codbar>` — monta um prompt com nome+marca+EAN do produto, pede pro Gemini (com `google_search`) pesquisar na internet e responder **só com JSON** (`{"imagens": [{"url", "titulo"}, ...]}`, até 6 candidatas) — nenhuma imagem é baixada nem salva nessa etapa, só as URLs voltam pro painel. O parsing extrai o primeiro bloco `{...}` do texto de resposta com regex (o modelo às vezes cerca o JSON com texto/comentário mesmo pedindo pra não fazer isso, ou responde só em texto livre quando não acha nada — nesses casos o regex não acha JSON e o resultado vira lista vazia sem erro, ver abaixo).
2. `POST /admin/definir-imagem-url/<codbar>` (body `{"url": "..."}`) — só quando o usuário clica numa das opções: baixa a URL escolhida no servidor e reaproveita `save_image_from_response` (mesma função usada por Bing/Google/Zaffari) pra salvar como a foto do produto, incluindo a remoção de fundo que já acontecia pras outras fontes. Registra no histórico com `origem='ia'`.

**Validação server-side das URLs antes de mostrar pro usuário** (`_url_e_imagem_valida`, HEAD com fallback pra GET em streaming, checando `Content-Type` começa com `image/`): apesar do prompt pedir explicitamente só links diretos de arquivo de imagem, o Gemini às vezes devolve o link de uma **página** de resultado (ex.: `toppng.com/png-e0t6...` sem extensão, uma página HTML que mostra a imagem, não o arquivo em si) ou uma URL de thumbnail do Wikimedia com um tamanho de pixel que não existe de verdade (404). Sem essa validação, o picker mostrava "N imagens encontradas" mas as miniaturas quebradas falhavam silenciosamente no `<img>` do navegador — bug real pego testando ao vivo (2 candidatas retornadas, 0 miniaturas exibidas, sem nenhuma explicação pro usuário). As checagens rodam **em paralelo** (`concurrent.futures.ThreadPoolExecutor`, até 6 candidatas ao mesmo tempo) — em série isso podia empilhar dezenas de segundos de timeout.

**Erro de API vs. "nada encontrado" — distinção importante**: `_buscar_imagens_gemini_web` retorna uma tupla `(candidatos, erro)`. Se a própria chamada ao Gemini falhar (chave inválida, rede, etc.), `erro` vem preenchido e a rota responde **502**, mostrado pro usuário no picker ("Erro ao buscar: ..."). Só quando a chamada teve sucesso mas o modelo genuinamente não achou nenhuma foto confiável (ou só achou links que não sobreviveram à validação) é que `candidatos` vem `[]` com `erro=None` — aí sim o picker mostra o estado vazio ("Nenhuma imagem encontrada na internet para este produto"), sem alarmar o usuário com um "erro". Essa distinção foi um bug real pego testando com a versão OpenAI (que tratava QUALQUER falha, incluindo a chave sem crédito, como lista vazia, escondendo um problema de configuração atrás de um "não achei nada" enganoso) — mantida ao trocar pro Gemini.

**Latência bem variável, não é bug**: como o Gemini com `google_search` pode disparar várias buscas reais antes de responder, o tempo de resposta observado em teste variou de ~2s a **~40s** pra exatamente o mesmo produto em chamadas diferentes. O botão mostra "Buscando na internet..." + o picker mostra "A IA está pesquisando na internet..." durante a espera — ao testar/depurar, dar tempo de sobra antes de considerar que travou.

**Picker inline, não modal/nova página** (`.ia-picker`, CSS perto de `.detail-modal-*`): grid de miniaturas 3 colunas dentro do próprio painel de detalhes (`#detail-ia-picker`/`#hist-detail-ia-picker`, escondido por padrão). Cada miniatura é um `<img>` carregado direto da URL já validada pelo servidor — mesmo assim, se uma falhar ao carregar no navegador (rede instável, hotlink bloqueado especificamente pro user-agent do navegador), ela se remove sozinha da grade (`onerror="this.closest('.ia-picker-item').remove()"`), como defesa extra além da validação server-side. Clicar numa miniatura desabilita a grade inteira, chama `admin_definir_imagem_url`, e em caso de sucesso atualiza a imagem do painel + fecha o picker + dispara o mesmo callback de "imagem resolvida" que os outros botões já usam (`loadConsulta`/`removerLinhaHistorico`, conforme o painel). Botão "×" fecha o picker sem escolher nada, a qualquer momento.

`buscarImagensIA(ean, btn, pickerSelector, imageSelector, onImagemDefinida)` é uma função **compartilhada** entre os dois painéis (não duplicada como o resto do painel do Histórico) — é só uma ação de botão autocontida (mesmo padrão de `gerarArteParaBotao`, que também já era compartilhada), não o painel inteiro, então não tem o mesmo risco de acoplamento que motivou duplicar o painel completo.

Testado de ponta a ponta num navegador real, produto de referência da sessão (Coca-Cola Sabor Original Pet 600ml, EAN 7894900011609): erro de API (quota da OpenAI esgotada) exibido corretamente no picker antes da troca pro Gemini; com o Gemini, candidata real encontrada, validada, exibida como miniatura, selecionada com um clique, baixada e salva como foto do produto (com remoção de fundo aplicada) — painel atualizado sozinho sem reload da página.

## Arte publicitária VERTICAL (terminal ET45 em pé) — pipeline irmã da horizontal

Pedido do usuário: suporte a um terminal montado em retrato (ET45, 10.1", `ARTE_LARGURA_VERTICAL`/`ARTE_ALTURA_VERTICAL` = **1200x1920** — resolução real do painel WUXGA 1920x1200 girado, mesma regra fixa "nunca assumir, sempre medir o aparelho real" do par horizontal). Veio depois de uma investigação no `mplayer` que mostrou que os layouts XML vertical (`price_check_vertical_image_top/bottom.xml`) já existiam prontos no app — o trabalho real ficou em (1) essa pipeline de arte nova aqui e (2) o app aprender a pedir/desenhar a orientação certa (ver CLAUDE.md do mplayer).

**Composição bem diferente da arte horizontal** (`compor_arte_vertical`, ao lado de `compor_texto_na_arte`): em vez de painel lateral + cena de fundo cobrindo a tela toda, é cena só na faixa de CIMA (45% da altura, `_normalizar_tamanho_arte` com `altura=altura_foto`) + painel de cor sólida (dominante extraída da própria foto, `_cor_painel_vibrante` — mesma função da horizontal) cobrindo a faixa de BAIXO (55%), com a borda de cima em curva (`_desenhar_painel_curvo_topo`, mesma sanoide de `_desenhar_painel_curvo` só que percorrendo a largura em vez da altura — o painel fica embaixo, não do lado). Gemini gerado em `aspect_ratio='4:3'` (mais próximo da proporção 1200:864 da faixa de cima que '16:9'), `gerar_arte_publicitaria_vertical` espelha `gerar_arte_publicitaria` no resto (mesmo prompt de cena `_montar_prompt_arte`, mesmo corte de tarja, mesmo registro de uso Gemini).

**Diferença deliberada mais importante: SEM preço desenhado na arte.** A arte horizontal também não desenha preço (fica pro app sobrepor), mas aqui foi um pedido explícito e discutido: "os preços vai retornar do cliente" — cada loja/integração tem seu preço em tempo real, gravar um valor fixo não faz sentido. Em vez de badge de preço, a arte reserva uma **caixa branca com sombra** (`ImageFilter.GaussianBlur`, mesmo efeito de elevação que o app já usa nativamente pro card de preço horizontal) no lugar onde o app vai desenhar o preço de verdade por cima depois — pedido do usuário: "quero uma caixa com efeito e sombra".

**Posição da caixa é FIXA (%), não derivada da quebra de linha do nome — decisão crítica pra o app conseguir replicar sem adivinhar**: `CAIXA_PRECO_Y0_PCT = 0.16` e `CAIXA_PRECO_ALTURA_PCT = 0.14`, ambas relativas a `altura_foto` (não a `y_texto`, que varia conforme o nome tem 1 ou 2 linhas). Isso existe porque o app (Kotlin, `updatePriceBadge` no mplayer) desenha o preço real DEPOIS, num processo totalmente separado, sem nenhuma visibilidade de quantas linhas o texto ocupou aqui no servidor — só com uma posição fixa (mesma % nos dois lados) os dois lados conseguem concordar de verdade sobre onde a caixa está. Se o nome for curto, sobra espaço em branco acima da caixa; aceitável, a alternativa (posição variável) quebraria a sincronia entre servidor e app.

**Nomes de arquivo/cache distintos da arte horizontal, pro mesmo EAN poder ter as duas ao mesmo tempo** (uma loja pode ter terminais dos dois tipos): `<codbar>_vertical.webp` em vez de `<codbar>.webp` (`_arte_url(codbar, orientacao='vertical')`). A fila única de geração (`_fila_arte`/`_worker_fila_arte`) passou a carregar `orientacao` em cada `_JobArte` e despachar pra `gerar_arte_publicitaria` ou `gerar_arte_publicitaria_vertical` conforme o job — continua garantindo no máximo uma chamada ao Gemini por vez, agora somando as duas orientações, não só uma. `_gerando_arte_em_andamento` (evita gerações concorrentes do mesmo produto) também precisou de uma chave composta (`_chave_andamento`): horizontal continua usando o `codbar` puro (não quebra nenhum código existente que já checava isso direto), vertical usa `f'{codbar}:vertical'` — uma geração vertical em andamento nunca bloqueia nem é bloqueada por uma horizontal do mesmo produto.

**Contrato HTTP**: `GET /produto-imagem/<codbar>` e `POST /produto-imagem/<codbar>/gerar-arte` ganharam um query param opcional `?orientacao=vertical` (default: horizontal, sem quebrar nenhum chamador existente que não manda esse param). O app manda esse valor de acordo com a orientação física do terminal (ver `isDeviceVertical()` no mplayer) — só a orientação pedida é gerada em background quando falta, nunca as duas de uma vez (cada chamada ao Gemini custa; não faz sentido gerar arte vertical pra uma loja que só tem terminal horizontal).

**Achado real durante o teste**: a autocura de arte (gera sozinha quando falta) significa que qualquer produto com foto crua eventualmente ganha `hasArt=true` pra QUALQUER orientação que seja pedida — inclusive testando a horizontal de propósito, o que quebrava a visualização vertical (o app caía no modo "arte em tela cheia" horizontal, esticada/errada, dentro do layout vertical). A separação de arquivo+cache por orientação (`_vertical.webp` vs `.webp`, chave de cache `_arte_vertical` vs `_arte` do lado do app) resolve isso — cada orientação só reage à sua própria arte, nunca à do outro terminal.

Testado de ponta a ponta via HTTP real (`GET /produto-imagem/<ean>?orientacao=vertical`, não só script avulso): gerou em exatamente 1200x1920, painel com cor dominante do produto, nome com hierarquia marca/resto, caixa branca com sombra na posição fixa — depois confirmado rodando de verdade no ET45 físico (ver CLAUDE.md do mplayer).

## Login real do painel (substituiu um bypass sério que existia antes)

Até esta sessão o painel **não tinha login de verdade**: `configuracoes.html` se autenticava sozinho no carregamento via `GET /painel/login`, uma rota que emitia um JWT válido pra `antunes@mupa.app` **sem checar senha nenhuma** — e, se essa rota falhasse, caía num fallback com as credenciais reais **hardcoded no próprio JavaScript** (visível a qualquer um vendo o código-fonte da página). Ou seja: `/configuracoes` era, na prática, uma página pública. Pedido do usuário pra corrigir isso ("adiciona um login" + "altere o index pra carregar o login"):

- **`GET /painel/login` foi removido** — não existe mais nenhum jeito de conseguir um token sem mandar credenciais reais.
- **`POST /login`** continua sendo o único jeito de autenticar, contra `CREDENCIAIS_PAINEL` (dict em `app.py`, atualmente `antunes@mupa.app` e `support@mupa.app` — adicionar um novo acesso é só adicionar uma entrada nesse dict).
- **Tela de login de verdade** em `configuracoes.html` (`#login-screen`): e-mail + senha, `POST /login`, token + `expires_at` salvos em `localStorage` (`mupa_painel_token`/`mupa_painel_token_expira`). Uma sessão salva e ainda válida (mesma janela de 1h do JWT) pula a tela de login no próximo carregamento; expirada ou ausente, sempre mostra a tela de login. Botão "Sair" na barra lateral limpa a sessão.
- **`GET /` (index)** não serve mais a ferramenta avulsa de remover fundo — só redireciona (302) pra `/configuracoes`, que decide sozinho se mostra a tela de login ou o painel (ver acima). A ferramenta de remover fundo continua existindo, só que migrou pra dentro do painel autenticado (ver seção "Aba Remover Fundo" abaixo).

Testado de ponta a ponta num navegador real: `GET /painel/login` agora dá 404; `GET /` dá 302 pra `/configuracoes`; senha errada é rejeitada (401) e mantém a tela de login; a credencial nova (`support@mupa.app`) loga normalmente e mostra o painel completo; sessão sobrevive a um reload da página (localStorage); "Sair" limpa tudo e volta pra tela de login.

### Tela de login redesenhada em duas colunas (pedido do usuário, com referência visual — estilo "Phylum"/onboarding SaaS moderno)

A tela de login original (card único centralizado, e-mail + senha empilhados) virou duas colunas: `.login-showcase` (painel escuro decorativo, gradiente + ícones flutuantes + headline/descrição do produto) ao lado de `.login-form-col` (o formulário de verdade, com campos com ícone à esquerda e botão de mostrar/ocultar senha). Só a CASCA visual mudou — todos os IDs funcionais (`#alert-login`, `#login-form`, `#login-email`, `#login-senha`, `#btn-login`) continuam exatamente iguais, então o JS de autenticação (`POST /login`, salvar token no localStorage, etc.) não precisou de nenhuma mudança.

- **`.login-showcase`**: gradiente escuro (`linear-gradient(160deg, var(--sidebar-bg), #1e1b4b, #312e81)`) + duas manchas de luz desfocadas via `filter:blur()` (decoração 100% CSS, sem nenhuma imagem pra carregar) + 4 "cartões flutuantes" com ícone (`.login-float-card`, reaproveitando ícones que o próprio painel já usa em outros lugares — imagem/tag/checklist/chave — em vez de uma ilustração customizada nova) espalhados pelo painel via `top`/`left` em `%` definidos como custom property (`--x`/`--y`/`--r` pra rotação) direto no atributo `style` de cada card no HTML.
- **Bug real pego testando, corrigido na mesma leva**: a primeira versão tinha `.login-showcase-cards { position:relative; height:0; }` (pensado pra não ocupar espaço de layout, já que os cards escapam via `position:absolute`) — mas isso é um erro clássico de CSS: `top` em `%` num container de altura `0` sempre resolve pra `0`, então os 4 cards ficavam todos empilhados exatamente no mesmo lugar (embaixo do painel, onde o container ficava por causa do `justify-content:space-between` do pai) em vez de espalhados como pretendido. Só percebido inspecionando `getBoundingClientRect()` dos 4 cards ao vivo (todos com `y≈756`, deveriam variar de ~60 a ~500) — visualmente né óbvio o bastante numa olhada rápida na screenshot, já que os cards ficavam parcialmente fora da view. Corrigido trocando pra `position:absolute; inset:0;` (preenche o painel inteiro, dando um tamanho real pras porcentagens resolverem contra).
- **Campos com ícone** (`.input-icon-wrap`/`.input-icon`): mesmo padrão de input já usado no resto do painel, só com `padding-left` extra pra abrir espaço pro ícone posicionado em `absolute` à esquerda — não é um componente novo do zero, é o input existente com um wrapper.
- **Mostrar/ocultar senha** (`#btn-toggle-senha`, novo): troca o `type` do `#login-senha` entre `password`/`text` e o próprio ícone do botão (olho aberto ↔ olho riscado) — melhoria de usabilidade real inspirada na referência, não só estética (senha longa é mais fácil de conferir antes de enviar).
- **Responsivo**: `.login-showcase` some inteiramente abaixo de 860px (`display:none`) — não faz sentido espremer um painel decorativo numa tela de celular, o formulário sozinho já ocupa a tela toda; `.login-form-brand` (marca + nome, escondida por padrão) aparece nesse caso pra não perder a identificação da marca quando a vitrine some.

Testado de ponta a ponta num navegador real: os 4 cards flutuantes conferidos via `getBoundingClientRect()` depois da correção (posições variadas, dentro dos limites do painel); toggle de mostrar/ocultar senha clicado de verdade (senha digitada aparece em texto plano, ícone troca); login completo (e-mail + senha reais, submit) funcionando de ponta a ponta sem nenhuma mudança no fluxo — token salvo, redirecionado pro painel; layout mobile (< 860px) conferido via DOM (`getComputedStyle` confirmando `.login-showcase{display:none}` e `.login-form-brand{display:flex}`, sem overflow horizontal na página).

#### Segunda rodada, com o usuário testando ao vivo e mandando print com setas: ícone sobrepondo o texto digitado, vitrine "melhore", pediu animações

**Bug real de CSS achado pelo usuário, não por mim**: nos campos de e-mail/senha, o ícone (posicionado em `absolute`) ficava por cima do começo do texto digitado/placeholder (`✉ce@mupa.app` em vez de `voce@mupa.app` com espaço pro ícone) — confirmado no print que o usuário mandou com uma seta apontando exatamente pro problema. Causa raiz: `.input-icon-wrap input { padding-left: 2.6rem }` e a regra genérica de input mais abaixo no arquivo (`input[type="email"], ... { padding: 0.55rem 0.75rem; ... }`) têm a **mesma especificidade CSS** (uma classe + um tipo, dos dois lados) — em empate de especificidade, quem vem DEPOIS no arquivo vence, e a regra genérica (que reseta o padding-left pro valor padrão, sem espaço pro ícone) vinha depois. Corrigido aumentando a especificidade do seletor (`.login-screen .input-icon-wrap input`, um ancestral a mais) em vez de `!important` — evita o mesmo problema se outra regra genérica for adicionada depois no arquivo. Confirmado via `getComputedStyle` (`padding-left` resolvendo pra `43.2px` = `2.7rem`, não mais o valor resetado).

**Vitrine lateral enriquecida** (pedido: "melhore a imagem da lateral"):
- **3º glow** (`.login-showcase-glow-3`, ciano) além dos 2 originais (índigo/violeta) — mais variação de cor, evita a composição ficar monocromática.
- **Textura de pontos** (`.login-showcase::before`, `radial-gradient` repetido em grade 26px, com uma máscara elíptica pra desvanecer nas bordas) — o tipo de detalhe "constelação"/blueprint comum em painel escuro de produto dev-tool, dá profundidade sem precisar de nenhuma imagem.
- **5º cartão flutuante** (ícone de gráfico de barras) — a composição original com 4 cards deixava uma área vazia grande no meio/topo do painel; um 5º preenche esse espaço.

**Animações adicionadas** (pedido explícito: "adicionar animações"), todas sutis/lentas de propósito — o objetivo é dar vida ao painel sem competir com o formulário, que é o que realmente importa na tela:
- **Entrada com fade+slide-up** (`loginFadeUp`, 0.6s) na marca, no texto de destaque e no formulário — com pequenos atrasos escalonados entre eles (marca → texto → formulário) em vez de tudo aparecer de uma vez.
- **Pulso lento nos glows** (`glowPulse`, 18s, `scale`+`translate`+opacidade) — bem devagar de propósito, mal dá pra perceber olhando direto, só cria uma sensação de "vivo" com o rabo do olho.
- **Balanço nos cartões flutuantes** (`loginFloat`, translateY sutil) — cada cartão com sua própria duração (6.5s–8.5s) e atraso (`--dur`/`--delay`, custom property no HTML de cada um) pra ficarem fora de sincronia uns dos outros, em vez de baloiçar tudo junto de forma robótica; mais uma entrada em escala (`loginCardIn`) quando a página carrega.

Reconferido depois das mudanças: `.login-float-card` conta 5 (era 4), `.login-showcase-glow` conta 3 (era 2), sem erro novo no console, layout mobile e login completo retestados de novo — nada quebrou com as adições.

## Aba "Remover Fundo" (migrada de `templates/index.html`, agora autenticada)

Existia uma ferramenta solta de remover fundo de imagem (upload ou URL, via `rembg`) servida direto na raiz (`templates/index.html`, Bootstrap/jQuery antigo, sem login nenhum). Virou uma aba normal do painel (`#tab-removerfundo`, ícone de imagem na barra lateral) — mesmas duas rotas de backend de sempre (`POST /remove_background_upload`, `POST /remove_background_url`), só que agora atrás de `@jwt_required()` (antes eram públicas, sem proteção nenhuma, qualquer um na internet podia processar imagens à vontade nelas). `templates/index.html` ficou órfão (sem rota apontando pra ele) — não foi apagado, mas pode ser removido com segurança se um dia isso incomodar.

Fluxo: escolher arquivo OU colar URL → botão "Remover fundo" → chama a rota correspondente com `authHeaders()` → mostra o resultado inline (imagem com fundo xadrez pra evidenciar a transparência) + link "Abrir em nova aba". Testado de ponta a ponta com uma imagem real do catálogo (Coca-Cola, EAN 7894900011609) — recorte limpo, resultado renderizado corretamente na aba.

## Arquitetura da arte publicitária (a parte mais delicada do projeto)

Fluxo: `GET /produto-imagem/<codbar>` → se já existe arte, retorna `imagem_url_arte`; se não existe mas há foto crua, dispara `gerar_arte_publicitaria` **em background** (thread separada, guardada por `_gerando_arte_em_andamento` pra não duplicar chamadas simultâneas) e retorna `null` nessa primeira resposta — a arte aparece só na consulta seguinte.

### Decisão arquitetural: "IA integra a cena, o app garante o texto"

Depois de iterar bastante (ver histórico de commits), a decisão final foi:
- **Gemini (`gemini-2.5-flash-image`) gera só a CENA/fotografia** com o produto integrado — nenhum texto escrito pela IA de imagem.
- **Nome do produto + headline são gerados por texto** (`gerar_textos_arte_ia`, modelo `gemini-2.5-flash-lite`) e **desenhados por PIL** (`compor_texto_na_arte`), com fonte real — isso garante ortografia 100% correta no card de texto, ao contrário de deixar o modelo de imagem "escrever" (ele erra letras).
- **Preço não faz parte da arte** — é sobreposto depois pelo app Android (`PlayerActivity.updatePriceBadge`), usando `product.priceSlots`. Por isso o `LAYOUT` do prompt reserva a metade esquerda inteira livre de qualquer coisa.

### `ARTE_PROMPT_TEMPLATE` — regras e por quê (não simplificar sem saber a razão)

Cada regra existe por causa de um bug real observado:

- **Categoria do produto no cenário** (comida vs. não-comida): sem essa regra, a IA interpretava nome/aroma do produto ao pé da letra — um desodorante "Dark Temptation" (aroma chocolate) virou uma cena de sobremesa com chocolate de verdade. Regra: só monta cenário de comida se o produto **for** alimento/bebida; caso contrário, cenário de uso real da categoria (banheiro, spa, rotina).
- **"Produto aparece uma única vez"**: sem essa regra, a IA às vezes duplicava o produto — uma cópia nítida na metade direita (correta) e uma segunda cópia borrada "vazando" pro fundo da metade esquerda, inclusive repetindo texto promocional impresso na embalagem (ex.: "Leve 5 Pague 4") duas vezes.
- **Vinheta lateral em todas as 4 bordas** (`_aplicar_vinheta`, função separada em Python, não faz parte do prompt): escurece sutilmente as bordas pra dar acabamento premium — implementada via gradiente de alpha (não numpy), combinando eixo horizontal + vertical com `ImageChops.lighter`.
- **Sem pessoas/rostos/mãos**: regra de compliance, não decoração.
- **Sem logo de terceiro duplicado**: um selo já impresso na embalagem (ex.: FIFA, campeonato licenciado) não pode ser recriado como elemento gráfico separado na composição.

### REGRA FIXA: a arte sempre sai em 1280x800 (dispositivo na horizontal) — nunca mudar

`_normalizar_tamanho_arte` (chamada em `compor_texto_na_arte`, logo depois de abrir a imagem e ANTES da vinheta/texto) força a arte final a sair **sempre** em `ARTE_LARGURA_HORIZONTAL x ARTE_ALTURA_HORIZONTAL` = **1280x800**, redimensionando com preservação de proporção e cortando o excedente (mesma lógica de um `CENTER_CROP`, feita aqui no servidor). Isso é uma regra explícita pedida pelo usuário, não uma escolha arbitrária — **nunca remover essa normalização ou deixar o tamanho variar**.

Por quê isso importa tanto: antes dessa normalização, `_cortar_tarjas_pretas` cortava uma quantidade *variável* de pixels a cada geração (dependendo de quanto letterboxing o Gemini incluiu naquela chamada específica), então o arquivo final saía com um tamanho ligeiramente diferente toda vez. Isso causava dois problemas visuais concretos, ambos reportados pelo usuário e confirmados durante a investigação:
1. O app faz `CENTER_CROP`/`FIT_CENTER` (ver histórico abaixo) pra exibir a arte — uma fonte de tamanho variável fazia cada imagem ser escalada numa proporção diferente, resultado imprevisível de produto pra produto.
2. A vinheta (`_aplicar_vinheta`) é desenhada em % da altura da imagem *nesse ponto do pipeline* — se o corte de letterboxing reduzia a altura antes da vinheta ser aplicada, o app depois escalava essa imagem (já menor) de volta pro tamanho da tela, e esse reescalonamento fazia a faixa de vinheta ficar fina demais ou sumir visualmente — parecia que o degradê tinha sido removido, mas o código nunca deixou de chamar `_aplicar_vinheta`; o efeito só ficava inconsistente por causa do tamanho variável de entrada.

**Por que 1280x800 e não 1344x768 (valor original, um 16:9 genérico "arredondado")**: o usuário mediu a resolução real do terminal físico via `adb shell wm size` (`Physical size: 1280x800`) e pediu pra usar esse valor exato em vez de uma suposição de proporção. Antes da troca, a arte (1344x768, proporção 1.75:1) não batia com a tela real (1280x800, proporção 1.6:1) — o app usava `FIT_CENTER` (ver seção do app abaixo) pra nunca cortar a arte, mas isso deixava uma tarja (letterbox) visível no topo/base por causa do descompasso de proporção. Com a arte gerada EXATAMENTE na resolução real do terminal, `FIT_CENTER` escala 1:1 e cobre a tela inteira sem cortar nada E sem nenhuma tarja — as duas exigências (nunca cortar / preencher a tela) deixam de ser conflitantes.

Isso significa que, **se a loja/terminal físico tiver uma resolução de tela diferente de 1280x800, esse valor precisa ser atualizado** (não é mais um 16:9 universal, é a resolução exata de um hardware específico) — rodar `adb shell wm size` no terminal em questão antes de mudar. Se um dia existirem terminais com resoluções diferentes ao mesmo tempo, essa constante única deixa de fazer sentido — seria necessário um `ARTE_LARGURA_HORIZONTAL`/`ARTE_ALTURA_HORIZONTAL` por perfil de dispositivo, não implementado ainda porque não foi pedido.

Se um dia existir suporte a terminal em modo retrato, ele precisa de uma constante de tamanho fixa própria (resolução real do terminal em pé, medida do mesmo jeito) — mas seguindo a mesma regra: nunca variável, sempre a resolução física real.

Verificado após a correção: art regenerada via `/admin/gerar-arte/<codbar>` saiu em exatamente `(1280, 800)` (`PIL.Image.size`), e testada de ponta a ponta no terminal físico (`SK100_Mupa`, serial `4001442606003389`) — arte cobrindo a tela inteira, sem corte nas bordas e sem tarja.

### Painel gráfico de cor sólida com borda em curva (redesign do texto, referência: campanhas reais tipo Coca-Cola)

O cartão escuro semi-transparente original foi substituído por um **painel de cor sólida cobrindo a metade esquerda inteira**, com a borda direita em curva orgânica (uma onda suave, `_desenhar_painel_curvo`) em vez de uma linha reta — visual bem mais forte, de campanha publicitária de verdade, pedido explicitamente pelo usuário mostrando uma peça real da Coca-Cola como referência.

- `_cor_painel_vibrante(cor_acento)`: a cor extraída da embalagem (`_extrair_cor_acento`) às vezes sai clara/pálida demais pra um painel grande de cor sólida — essa função força saturação mínima e um brilho médio-escuro fixo (via HSV) pra sempre ter aquele efeito "cor de marca forte" (tipo o vermelho da Coca-Cola), sem depender de sorte na extração.
- `_desenhar_painel_curvo`: desenha o painel como um polígono cujo lado direito segue uma curva senoidal suave, não uma linha reta — e retorna o x mais à esquerda que a curva alcança, usado como limite seguro pro texto nunca colidir com a onda.
- O painel é **totalmente opaco** (alpha 255, não semi-transparente como o cartão antigo) — cobre completamente o cenário nessa metade, então o prompt (`LAYOUT`) foi ajustado pra deixar claro que a IA não precisa caprichar visualmente nessa área, só mantê-la limpa (sem texto/produto), porque o painel cobre tudo depois.
- Texto (nome + sublinhado branco + headline) fica na faixa superior do painel (começa ~13% da altura) — deixa espaço vazio na faixa inferior (~92% da altura) porque é ali que o app Android sobrepõe o preço depois (`PlayerActivity.updatePriceBadge`); o painel sendo full-height serve de fundo bonito pro preço também, não só pro texto.
- Prompt também ganhou ênfase em **gotas de condensação realistas** pra bebidas geladas (regra nova em CONCEITO VISUAL) e uma referência explícita de padrão de qualidade ("campanha real de grandes marcas como Coca-Cola/Nestlé/Ambev") em vez de só "premium genérico".

Testado gerando a arte do produto EXATO da referência do usuário (Coca-Cola Sabor Original Pet 600ml, EAN 7894900011609) — resultado visualmente muito próximo do exemplo mostrado: painel vermelho com curva, título em negrito com sublinhado, garrafa com condensação realista, cena de mesa/jardim apetitosa que a própria IA compôs dentro das regras.

**Condensação suavizada depois** — a instrução original ("cubra a embalagem com GOTAS DE CONDENSAÇÃO realistas e **abundantes**... superfície molhada/brilhante") saía pesada demais em testes seguintes (garrafa toda molhada, filetes escorrendo, às vezes prejudicando a legibilidade do rótulo). Trocada por uma versão mais comedida: "leve toque de condensação, sutil e discreto (algumas gotículas pequenas e esparsas, sem filetes escorrendo nem superfície toda molhada)... a etiqueta e o design do produto continuam totalmente legíveis". Testado de novo na mesma Coca-Cola — poucas gotículas discretas, rótulo 100% legível, ainda comunica "gelado" sem dominar a cena.

### Ajustes seguintes (benefícios à direita, cor fiel ao produto, quantidade sempre visível)

Depois do primeiro resultado, mais 4 ajustes pedidos pelo usuário:

1. **Cor do painel sempre combinando com o produto**: `_extrair_cor_acento` tinha um fallback fixo vermelho (200,30,30) — funcionava bem pra produtos vermelhos por coincidência, mas ficava visualmente ERRADO pra qualquer outro produto quando a extração falhava (embalagem muito neutra/acromática). Trocado pra um cinza-chumbo neutro (45,48,56), que nunca destoa de nenhum produto. Também afrouxado o limiar de saturação (0.35→0.28) e aumentada a granularidade do quantize (8→12 cores) pra achar a cor dominante com mais precisão. Testado num produto verde (Dove Men+Care) — painel saiu verde, não mais vermelho por padrão.
2. **Produto sempre 100% visível**: reduzido o alcance máximo da curva do painel (base 0.47→0.44, amplitude 0.045→0.035 da LARGURA, não da altura — era um bug de unidade) pra nunca chegar perto dos 50% e arriscar cobrir o produto; e reforçada a regra no prompt (`ARTE_PROMPT_TEMPLATE`) proibindo qualquer corte do produto pelas bordas.
3. **Quantidade/tamanho da embalagem sempre visível** (ex.: 600ml, 1kg, 2L): a IA recebeu instrução explícita pra sempre incluir esse dado no nome gerado, mas ainda assim omitia às vezes — e mesmo quando incluía, o nome ficava tão longo que a linha com a quantidade era cortada pelo limite de linhas do título. Solução definitiva: `_extrair_quantidade_embalagem` (regex) SEMPRE remove a quantidade de dentro da string do nome (se a IA tiver incluído) e retorna ela separada; `compor_texto_na_arte` desenha a quantidade como uma linha PRÓPRIA e garantida logo após o nome (até 3 linhas) — nunca mais disputando espaço/sendo cortada junto com o resto do nome.
4. **Bullets de benefício movidos pro lado direito** (sobre a foto do produto, não mais no painel esquerdo) + **fonte da headline 40% menor**: o painel esquerdo agora só tem nome + quantidade + headline (bem mais compacto), deixando a maior parte da faixa inferior vazia pro card de preço que o app Android sobrepõe depois — era isso que "os benefícios no painel esquerdo" estava disputando espaço com. Do lado direito, os 3 bullets ficam encostados na borda direita, empilhados e centralizados verticalmente, cada um com um círculo na cor do painel + checkmark branco + texto com sombra escura (`_desenhar_texto_com_sombra`) — sombra necessária porque, ao contrário do painel de cor sólida, aqui o texto fica sobre a cena gerada pela IA, sem uma cor de fundo previsível atrás.

Retorno de `gerar_textos_arte_ia` mudou de `(nome, headline)` para `(nome, headline, beneficios, quantidade, marca)` — qualquer código futuro que chame essa função direto (fora de `gerar_arte_publicitaria`) precisa desempacotar os 5 valores.

### Prioridade da fonte da descrição: banco → Cosmos → Open Food Facts → Zaffari → Google → PreçoMelhor (sempre, não só quando corrompido)

Cogitamos primeiro usar o nome que a API de preço PRÓPRIA de cada cliente/loja retorna (mais específico por estabelecimento, mas tipicamente abreviado — ex.: "REFRIG COCA COLA 600ML") como fonte pro nome da arte, e cheguei a implementar isso (mplayer enviando `nome_cliente` na query string pro `produto-imagem/<ean>/gerar-arte`). **O usuário pediu pra reverter** — decisão final foi manter a fonte só no lado do produtos-imgs, sem depender do app enviar nada extra:

1. `produto.description` (nosso banco) primeiro.
2. Se estiver **vazio OU corrompido** (antes só disparava por corrupção — `not descricao_fonte.strip()` foi adicionado como segundo gatilho), busca pelo EAN nessa ordem: Cosmos → Open Food Facts → Zaffari → Google (`fetch_product_from_google`, usa uma busca de imagem com Custom Search API que às vezes retorna um título de produto útil; nota: o dict que essa função retorna tem `marca` como string solta, não `brand: {name}` aninhado como as outras fontes — o código já trata os dois formatos) → **PreçoMelhor** (`fetch_product_from_precomelhor`, adicionado por último na cadeia, ver seção própria abaixo).
3. Só DEPOIS de resolvida a melhor descrição bruta disponível é que a IA entra pra reconstruir/limpar o nome comercial final.

### Nova fonte: PreçoMelhor (precomelhor.com.br) — nome/marca, e agora também imagem real

`fetch_product_from_precomelhor(ean)` consulta a API pública e gratuita do PreçoMelhor: `GET https://www.precomelhor.com.br/api/nutrition-lookup?ean=<ean>`. Documentada abertamente no próprio site deles (`precomelhor.com.br` → "Ferramentas & APIs Gratuitas" → seção "Desenvolvedores"), sem necessidade de chave/token.

**Particularidade importante, só descoberta testando na prática** (o `curl` direto tomou `403` — proteção anti-bot da Cloudflare naquele momento; testei via browser real pra confirmar o contrato, embora numa checagem posterior o `curl` direto tenha voltado a funcionar sem bloqueio — o bloqueio parece intermitente, não confiar que vai sempre passar): o campo `success` do JSON vem **sempre `true`**, mesmo pra um EAN que não existe na base deles — o sinal real de "não encontrado" é `product_name` vindo como string vazia (`""`), não o campo `success`. `fetch_product_from_precomelhor` checa isso corretamente (`if not description: return None`), mas qualquer código novo que chamar essa API direto precisa saber disso — confiar só em `success` faria o app achar que TODO EAN foi encontrado.

Adicionado nas 3 cadeias de fallback de DESCRIÇÃO (fim da lista, prioridade mais baixa por ser a fonte mais nova/menos testada em produção): a rota `GET /produto/<codbar>` (cadastro automático genérico), o loop de correção de texto corrompido em `gerar_textos_arte_ia`, e o auto-cadastro dentro de `gerar_arte_publica` (`POST /produto-imagem/<ean>/gerar-arte`). Testado de ponta a ponta com o EAN de exemplo do usuário (`7896577211627`, Pepinos em Conserva Agridoce Fatiado Petry 440g) — `register_product_in_database` cadastrou corretamente `description`/`marca`, registro removido depois só por ser dado de teste.

Nenhuma mudança foi mantida no mplayer por causa disso (a tentativa de passar `nome_cliente` foi revertida por completo).

#### PreçoMelhor também como fonte de IMAGEM (pedido do usuário, corrigindo uma suposição errada anterior)

O parágrafo acima documentava que o endpoint de imagem do PreçoMelhor (`/api/image/<ean>?w=200`) só devolve um SVG placeholder genérico ("Sem Imagem") — isso continua **verdade**, mas é só um endpoint específico, não a única forma de ter imagem de lá. O usuário mandou um link real de um produto no site deles (`precomelhor.com.br/p/<ean>`, a página pública de detalhe) pedindo pra adicionar essa fonte também na busca/cadastro de imagem — inspecionando essa página ao vivo, o `<meta property="og:image">` dela às vezes aponta pra uma foto real hospedada no CDN próprio deles (Cloudflare R2 público, ex.: `pub-251da151f43b454d9e192d38bf5e6d71.r2.dev/<ean>.webp` ou `.jpg`) — bem diferente do endpoint de dados nutricionais, que nunca tem imagem nenhuma.

- **`_buscar_imagem_real_precomelhor(ean)`**: faz `GET https://www.precomelhor.com.br/p/<ean>` e extrai a URL do `og:image` via regex (`<meta\s+property="og:image"\s+content="([^"]+)"`, confirmado como o formato exato da tag nessa página). **O sinal de "é uma foto real" é o host da URL ser `r2.dev`** — quando o produto existe na base deles mas não tem foto própria cadastrada, o `og:image` aponta em vez disso pro mesmo endpoint placeholder do domínio principal (`precomelhor.com.br/api/image/<ean>...`), sempre o SVG genérico — então qualquer URL que não seja do `r2.dev` é tratada como "sem foto real" e descartada. `404` na página (EAN não existe na base deles, ex.: `7896204360520` do link que o usuário mandou) também retorna `None` sem levantar erro. Confirmado com vários EANs reais: alguns produtos têm foto própria de verdade (`r2.dev`), outros existem na base mas só com o placeholder (ex.: `7898098680128`, cujo `og:image` aponta pro endpoint placeholder mesmo aparecendo com uma miniatura real em listas de "produtos relacionados" de OUTRAS páginas — inconsistência do próprio site deles, não afeta a lógica aqui porque só a página do próprio EAN é consultada).
- **`buscar_e_salvar_imagem_precomelhor(codbar)`**: mesmo padrão de `buscar_e_salvar_imagem_bing/google/zaffari` — baixa a URL resolvida por `_buscar_imagem_real_precomelhor` e salva via `save_image_from_response` (com remoção de fundo incluída, igual as outras fontes). Adicionada como **último** passo (depois de Zaffari) nas 3 cadeias de busca de foto crua que já existiam: `obter_imagem_produto` (`GET /produto-imagem/<codbar>`, usada pelo terminal), `admin_buscar_imagem` (botão "Buscar imagem" do painel) e `serialize_produto_with_image` (usada por `GET /produtos`). Testado de ponta a ponta com produtos reais do catálogo sem foto (`7891149108282`, Refrigerante Sukita Laranja 200ml) — baixou, removeu fundo e marcou `tem_foto=True` corretamente; produto ficou com a foto de verdade (não é dado de teste descartável, era um produto real do catálogo que genuinamente não tinha imagem ainda).
- **`fetch_product_from_precomelhor` (cadastro automático) também ganhou imagem real**: o campo `thumbnail` do dict que essa função retorna, que antes era sempre a string fixa `'Imagem não disponível'`, agora chama `_buscar_imagem_real_precomelhor(ean)` e usa a URL real quando existe — os pontos que já consomem esse `thumbnail` (`register_product_in_database` e o auto-cadastro em `gerar_arte_publica`, que já checavam `thumbnail.startswith('http')` antes de baixar) passam a baixar a foto automaticamente sem precisar de nenhuma mudança adicional neles. Testado direto (`fetch_product_from_precomelhor('7896481170706')`) confirmando o `thumbnail` vindo como URL real do R2 quando disponível.

### Nova fonte de IMAGEM: Rissul (rissul.com.br) — mesma API pública VTEX já usada pela Zaffari

Pedido do usuário, mandando o link de um produto real (`rissul.com.br/cafe-a-vacuo-melitta-tradicional-500g-361118/p`). O Rissul (rede de supermercados) roda a loja online em cima da **VTEX** — a mesma plataforma da Zaffari — então tem a mesma API pública de busca de catálogo (`/api/catalog_system/pub/products/search`), só numa conta VTEX diferente (`superrissul`, descoberta pelo domínio dos assets de imagem da página, `superrissul.vtexassets.com`). Confirmado testando ao vivo: `GET https://superrissul.vtexcommercestable.com.br/api/catalog_system/pub/products/search?fq=alternateIds_Ean:<ean>` devolve exatamente o mesmo formato de resposta que `ZAFFARI_SEARCH_URL` já usa (lista de produtos, cada um com `items[].ean` e `items[].images[].imageUrl`) — sem chave/token, sem bloqueio de Cloudflare (`curl` direto funciona). EAN não encontrado retorna `200` com lista vazia (`[]`), não erro.

- **`RISSUL_SEARCH_URL`** (constante, ao lado de `ZAFFARI_SEARCH_URL`) + **`buscar_e_salvar_imagem_rissul(codbar)`**: cópia quase literal de `buscar_e_salvar_imagem_zaffari`, só trocando a URL base — mesmo contrato, mesma forma de extrair `imageUrl` e salvar via `save_image_from_response`. Adicionada como **último** passo (depois de PreçoMelhor) nas mesmas 3 cadeias de busca de foto crua: `obter_imagem_produto` (terminal), `admin_buscar_imagem` (botão do painel) e `serialize_produto_with_image` (`GET /produtos`) — a cadeia completa hoje é local → Bing → Google → Zaffari → PreçoMelhor → Rissul.

### Nova fonte de IMAGEM: Sonda Delivery (sondadelivery.com.br) — raspagem de HTML, sem API pública

Pedido do usuário, mandando um link de imagem de exemplo (`sondadelivery.com.br/Arquivos/ProdutosSku/1000047566/7898909864181.png`) — **por coincidência** (não intencional, mas verificado antes de qualquer coisa) o EAN desse exemplo é exatamente o do incidente da imagem imprópria (ver seção abaixo). Antes de integrar qualquer coisa, a imagem foi checada pelo nosso próprio classificador (`_imagem_e_segura`, baixada e testada isoladamente, sem persistir em disco) — deu `SEGURA`. Investigando a origem: `GET /delivery/busca/7898909864181` no próprio site confirma que esse EAN é "Steak vegetal proteína Soja Mania 110g" (bate com o que o Rissul já tinha achado pra esse EAN numa leva anterior) — reforça que o mapeamento ruim era específico da base do PreçoMelhor, não do EAN em si.

**Diferente de todas as fontes anteriores**: Zaffari/Rissul são API VTEX limpa (JSON), PreçoMelhor é uma tag `og:image` isolada numa página simples. O Sonda roda em **ASP.NET WebForms** com busca via widget de terceiro (SmartHint) — não tem API JSON pública conhecida. A integração é 100% raspagem de HTML:

- **`_buscar_imagem_real_sonda(ean)`**: faz `GET /delivery/busca/<ean>` (funciona via `requests` puro, sem precisar executar JS — confirmado ao vivo) e extrai via regex o `item_id` de dentro de um bloco de analytics (`gtag`) embutido no HTML da página de resultado (`item_id: "<sku>"`) — esse `item_id` é o SKU do primeiro resultado da busca. Monta a URL final: `https://www.sondadelivery.com.br/img.aspx/sku/<sku>/800/<ean>.png` (`SONDA_IMG_TAMANHO = 800`, parâmetro de largura em pixels do endpoint de redimensionamento). EAN sem resultado nenhum: página `200` sem `item_id` no HTML → regex não acha nada → `None`, sem erro (confirmado testando com EAN inválido/inexistente).
- **Achado crítico testando ao vivo, por que o SKU não é opcional**: o endpoint de imagem (`/img.aspx/sku/<sku>/<tamanho>/<ean>.<ext>`) **não valida o SKU** — um SKU errado ou fake (`0`, `999999`, etc.) não dá erro nenhum, devolve silenciosamente um placeholder genérico de tamanho **sempre igual** (4434 bytes, confirmado testando com EANs e SKUs diferentes, o tamanho do arquivo nunca muda). Sem descobrir o SKU certo via busca primeiro, a integração pareceria funcionar (sempre `200`) mas estaria salvando a mesma imagem de placeholder genérica pra qualquer produto — silenciosamente, sem nenhum sinal de erro. Por isso o SKU é resolvido via busca a cada chamada, nunca hardcoded nem pulado.
- **`buscar_e_salvar_imagem_sonda(codbar)`**: mesmo padrão de `buscar_e_salvar_imagem_precomelhor` — baixa a URL resolvida e salva via `save_image_from_response` (chokepoint de sempre: passa pelo classificador `_imagem_e_segura` antes de gravar, com remoção de fundo incluída se aprovada). Adicionada como **último** passo (depois de Rissul) nas 3 cadeias de busca de foto crua: `obter_imagem_produto` (terminal), `admin_buscar_imagem` (botão do painel) e `serialize_produto_with_image` (`GET /produtos`) — cadeia completa hoje: local → Bing → Google → Zaffari → PreçoMelhor → Rissul → Sonda. Nome **não** entra em `FONTES_OCULTAS_NO_PAINEL` — aparece normalmente nos rótulos/mensagens, mesmo tratamento que o PreçoMelhor já tinha (só Zaffari/Rissul ficam ocultos, por pedido específico anterior).
- **Mesma ressalva que já vale pras outras fontes raspadas**: só o PRIMEIRO resultado da busca é usado — se a busca do SmartHint não for um match exato pro EAN (query parecida, mas produto errado), a imagem salva pode ser de outro produto. A defesa de verdade contra conteúdo genuinamente impróprio continua sendo `_imagem_e_segura`, não a precisão da busca em si — mesmo princípio de "nenhuma fonte é 100% confiável" já documentado no incidente abaixo.
- Testado de ponta a ponta com produto real do catálogo sem foto (`7891910000197`) — resolveu o SKU (`1000001025`) via busca, baixou a imagem em 800px, classificada `SEGURA` pelo filtro, salva em `IMAGES_FOLDER`+`PROCESSED_IMAGES_FOLDER` (com remoção de fundo) e `tem_foto` marcado `True`; produto real do catálogo, gap genuíno preenchido, não dado de teste descartável.

### Nova fonte de IMAGEM: Unidasul (Azure Blob Storage, sem busca — nome do blob já é o EAN)

Pedido do usuário, mandando uma URL de container do Azure com SAS token: `https://sabancoimagenspng.blob.core.windows.net/png1000x1000?<sas-token>`. Diferente de TODAS as outras fontes (nenhuma tinha API JSON limpa nem nome de arquivo previsível sem antes buscar) — aqui não tem busca nenhuma: o SAS token dado tinha permissão de **listagem** (`sp=rl`, `r`=read `l`=list), então listei o container direto (`GET ...?restype=container&comp=list&<sas-token>`) e confirmei que o nome de cada blob já É o EAN: `<ean>_1.png` (ex.: `0038000116193_1.png`). Isso simplifica a integração pro mínimo possível: monta a URL, confere com `HEAD` se existe, baixa se existir.

- **`UNIDASUL_SAS_TOKEN`** (Config, só a query string do SAS, sem a URL base) — card próprio em Configurações ("Token Unidasul (Azure Blob)"), mesmo padrão de token editável no painel que Cosmos/Gemini/OpenAI já tinham. **Motivo de ficar no banco e não no código**: um SAS token da Azure sempre tem validade (`se=` na própria query string, o token de exemplo expira em 2027-03-19) — quando vencer, alguém só cola o token novo no painel, sem precisar de deploy nenhum.
- **`_buscar_imagem_real_unidasul(ean)`**: lê o token do Config; se não tiver token configurado, retorna `None` direto (fonte fica inerte, sem tentar nada — mesmo comportamento de "não configurado" que outras integrações já têm). Monta `f'{UNIDASUL_BLOB_BASE_URL}/{ean}_1.png?{token}'` e confere com `HEAD` (mais barato que baixar o arquivo inteiro só pra saber se existe) — `200` retorna a URL, qualquer outro status (`404` pra EAN sem blob, token expirado também dá erro aqui) retorna `None`.
- **`buscar_e_salvar_imagem_unidasul(codbar)`**: mesmo padrão de sempre — baixa a URL resolvida e salva via `save_image_from_response` (chokepoint de sempre, passa pelo `_imagem_e_segura` antes de gravar). Adicionada como **último** passo (depois de Sonda) nas 3 cadeias de busca de foto crua — cadeia completa hoje: local → Bing → Google → Zaffari → PreçoMelhor → Rissul → Sonda → Unidasul. Nome aparece normalmente nos rótulos/mensagens (não entra em `FONTES_OCULTAS_NO_PAINEL`).
- Testado de ponta a ponta: listagem do container confirmou o padrão de nome; `HEAD` retornou `200` pra um EAN real do container e `404` pra um EAN inventado; `buscar_e_salvar_imagem_unidasul` baixou, salvou (`IMAGES_FOLDER`+`PROCESSED_IMAGES_FOLDER`) e retornou a URL correta pra um EAN de teste descartável (`0038000116193`, nenhum produto do nosso catálogo — não sobrou resíduo, arquivos removidos depois do teste).

**Achado importante, sem relação com a Unidasul especificamente — sinalizado ao usuário na hora**: durante esse teste, `_imagem_e_segura` (o classificador de conteúdo impróprio, ver seção do incidente abaixo) falhou com `403 PERMISSION_DENIED` / `BILLING_DISABLED` do Google Cloud — a chave Gemini configurada **nesta máquina de dev** está num projeto sem faturamento habilitado no momento. Por causa do "fail-open" deliberado (`_imagem_e_segura` permite salvar quando a classificação dá erro, ver seção do incidente), a imagem de teste foi salva mesmo assim, sem passar pela checagem de segurança de verdade — o filtro proativo está **efetivamente desligado nesta máquina** até o faturamento do projeto Google Cloud ser reativado. Não confirmado ainda se o mesmo projeto/chave é usada no `srv-mupa` (cada `instance/produtos.db` guarda sua própria `GEMINI_API_KEY` na tabela Config, então pode ser uma chave diferente lá) — mas vale conferir o status de faturamento em produção também, já que esse é exatamente o mecanismo que evita a repetição do incidente do EAN `7898909864181`.

### Toggle individual por fonte de imagem: liga/desliga + "revisão obrigatória"

Pedido do usuário depois de discutir o quanto o filtro de conteúdo (`_imagem_e_segura`) pode falhar (ver seção "garantia de segurança" logo abaixo): complementar ao kill switch geral (`BUSCA_IMAGEM_ONLINE_ATIVA`, que desliga TODAS as fontes de uma vez), agora dá pra controlar cada fonte individualmente em Configurações → "Fontes de Imagem" (tabela com Bing/Google/Zaffari/PreçoMelhor/Rissul/Sonda/Unidasul), com DOIS controles independentes por fonte:

- **Ativa** (`FONTE_<NOME>_ATIVA`, Config, default `'true'`): liga/desliga essa fonte específica na cadeia de busca, sem afetar as outras. `_fonte_imagem_ativa(fonte, cfg=None)` faz a checagem; `cfg` opcional evita reler `_ler_todas_config()` uma vez por fonte dentro do mesmo loop.
- **Revisão obrigatória** (`FONTE_<NOME>_REVISAO_OBRIGATORIA`, Config, default `'false'`): pedido explícito do usuário, dando o exemplo do PreçoMelhor (a fonte do incidente real) — a fonte continua buscando normalmente, mas **toda** imagem que vier dela cai em quarentena pra revisão humana antes de virar a foto do produto, **mesmo que `_imagem_e_segura` classifique como segura**. Não é uma segunda checagem de conteúdo — é uma política "não confio o suficiente nessa fonte pra aprovar automaticamente, mesmo quando a IA diz que tá tudo bem". `_fonte_exige_revisao(fonte, cfg=None)` faz a checagem.

**Onde entram**: as 3 cadeias de busca (`obter_imagem_produto`, `admin_buscar_imagem`, `serialize_produto_with_image` — essa última foi refatorada de um `if/elif` aninhado repetindo a mesma lógica 7 vezes pro mesmo padrão de loop das outras duas, já que checar o toggle dentro de um loop é bem mais simples) pulam a fonte inteira (nem tentam) quando "Ativa" está desligada. "Revisão obrigatória" é checada dentro de `save_image_from_response` — o mesmo chokepoint de sempre — junto da checagem de `_imagem_e_segura`: `reprovada or revisao_obrigatoria` decide se vai pra quarentena, com uma mensagem de log/resposta diferente pra cada motivo (conteúdo impróprio vs. política de fonte), mas o mecanismo de quarentena em si (`_quarentenar_imagem`) é o mesmo — cria a linha em `ImagemQuarentena`, bloqueia o EAN na hora, humano decide depois (confirmar/liberar).

**Backend, uma action genérica pras 14 combinações** (7 fontes × 2 toggles) em vez de 14 blocos quase idênticos no dispatcher de `/configuracoes`: o nome da fonte E qual dos dois toggles vêm do próprio nome da action (`toggle_fonte_precomelhor_ativa` / `toggle_fonte_precomelhor_revisao_obrigatoria`), que já bate exatamente com o que o fallback genérico do clique de toggle no frontend gera sozinho a partir do `data-key` (sem precisar adicionar nenhuma entrada nova no `actionMap` do JS).

Testado com script isolado: toggle "revisão obrigatória" da PreçoMelhor ligado via API; uma imagem SEGURA de verdade (a mesma foto de referência Coca-Cola, sem nada de impróprio) passada com `origem='precomelhor'` — confirmado indo pra quarentena mesmo assim (`origem` da linha de quarentena = 'precomelhor', EAN bloqueado), com o log deixando claro que o motivo foi a política da fonte, não o classificador. Dados de teste e a flag de teste removidos depois.

### "Podemos garantir que nenhuma imagem imprópria vai ser disponibilizada?" — resposta honesta pro usuário, registrada aqui pra não esquecer

O usuário perguntou isso diretamente. A resposta foi **não, não 100%**, com os motivos concretos:

1. **Achado crítico ainda não resolvido**: a chave Gemini de PRODUÇÃO (confirmado com o banco real do `srv-mupa`, não só nesta máquina) está com faturamento desabilitado — `_imagem_e_segura` falha em toda chamada agora, e por causa do fail-open (ver seção do incidente), toda imagem nova está sendo salva **sem checagem nenhuma** até isso ser corrigido. Esse é o problema mais urgente, resolve o resto praticamente sozinho.
2. **Fail-open é deliberado, não acidente**: qualquer falha de classificação (chave inválida, rede fora, cota esgotada, faturamento desabilitado) libera a imagem em vez de travar a busca inteira — escolha consciente de disponibilidade sobre bloqueio total.
3. **Classificador é uma IA, não uma regra determinística** — testado contra a imagem real do incidente e fotos normais sem falso positivo/negativo nesses casos específicos, mas isso não é uma garantia formal.
4. **A arte publicitária GERADA nunca passa por `_imagem_e_segura`** — só a foto crua de referência passa antes de virar input da IA de imagem. A arte final depende só do filtro nativo do próprio Gemini na geração, não auditado por nós.
5. **Imagens já salvas antes do filtro existir** só são pegas rodando `scripts/auditoria_seguranca_imagens.py` manualmente — já rodado localmente (219 imagens, 1 imprópria encontrada), nunca rodado no `srv-mupa` real nem na VPS (que ainda não tem as imagens transferidas).
6. **`/upload-multiplas-imagens`** (rota legada, sem uso pelo frontend) nunca passou pelo classificador — não corrigido, por ser código morto.

O toggle "revisão obrigatória" acima é uma resposta direta a esse limite: dá uma ferramenta pra reduzir a EXPOSIÇÃO a uma fonte específica sem depender só do classificador (que pode estar falhando, como está agora) — mas não substitui corrigir o problema de faturamento, que é o que está realmente quebrado hoje.

## Incidente real: imagem imprópria retornada pro EAN 7898909864181 — causa raiz real, kill switch, bloqueio permanente por EAN, filtro de conteúdo proativo

Usuário reportou ao vivo, em produção: o EAN `7898909864181` estava retornando uma **imagem pornográfica**. Investigado e corrigido em VÁRIAS rodadas — a causa raiz suspeita inicialmente (Google) estava **errada**, só descoberta depois que o mesmo EAN reproduziu o problema de novo neste ambiente de dev, com prints reais mostrados pelo usuário.

### Primeira suspeita (Google Custom Search sem SafeSearch) — correção válida, mas não era a causa raiz real

`fetch_product_from_google`/`buscar_e_salvar_imagem_google` montavam a query do Custom Search JSON API só com `q={ean}` (número puro do código de barras) e **sem o parâmetro `safe=`** — corrigido adicionando `&safe=active` nas duas URLs. Essa correção continua válida como boa prática (uma busca de imagem por dígitos crus, sem SafeSearch, é genuinamente arriscada), mas na hora não deu pra confirmar se era essa a causa real: a cota diária gratuita do Google Custom Search (100 buscas/dia) já estava esgotada, impedindo reproduzir o incidente ao vivo.

### Causa raiz REAL, confirmada com o EAN reproduzindo o problema de novo neste mesmo ambiente: PreçoMelhor, não Google

Testando o kill switch (ver abaixo), o mesmo EAN voltou a retornar a imagem imprópria — dessa vez capturada e confirmada visualmente (usuário mandou print do painel + a URL `GET /produto-imagem/7898909864181` retornando `static/processed_images/7898909864181.png`, e a imagem salva nesse arquivo era de fato conteúdo explícito). O log do servidor nesse momento mostrou: Bing falhou (410, morto), **Google nem chegou a rodar** (429, cota ainda esgotada — ou seja, a correção do SafeSearch nunca chegou a ser exercitada nesse teste), Zaffari não achou nada, e a imagem foi salva logo em seguida — sobrando só PreçoMelhor ou Rissul como candidatos. Testado direto: `_buscar_imagem_real_precomelhor('7898909864181')` retornou `https://pub-251da151f43b454d9e192d38bf5e6d71.r2.dev/7898909864181.jpg` (o CDN do **PreçoMelhor**, a mesma fonte integrada numa leva anterior desta sessão como "foto real curada"), enquanto a busca equivalente no Rissul pra esse EAN retornou uma foto de um produto completamente diferente e legítimo (Empanado de Soja Mania Vegetal) — ou seja, **o mapeamento ruim EAN→imagem existe especificamente na base de dados do PreçoMelhor**, não é um problema de relevância de busca (como se suspeitava do Google) nem de código nosso.

**Implicação importante, registrada aqui pra não repetir o erro de confiança**: o PreçoMelhor foi integrado assumindo que, por ter uma página de produto "curada" com imagem hospedada no próprio CDN deles (distinta do endpoint placeholder), esse mapeamento EAN→imagem seria confiável. Esse incidente prova que não é — mesmo uma fonte com imagem "real" hospedada em CDN próprio pode ter dado errado/malicioso pra um EAN específico. Nenhuma das fontes automáticas (Bing morto à parte) deve ser tratada como 100% confiável; a mitigação de verdade não é confiar mais ou menos numa fonte, é ter como **bloquear um EAN especificamente** quando um problema for encontrado (ver "Bloqueio permanente por EAN" abaixo) — isso é fonte-agnóstico e funciona não importa QUAL fonte trouxe o problema da próxima vez.

### Recursos pedidos em seguida, pra reagir mais rápido da próxima vez sem precisar de mim

**1. Kill switch "Busca de imagem online"** (Configurações → Flags de Funcionamento, toggle `BUSCA_IMAGEM_ONLINE_ATIVA`, default `true`): quando desativado, `_busca_imagem_online_ativa()` faz as 3 cadeias de busca de foto crua (`obter_imagem_produto`/terminal, `admin_buscar_imagem`/painel, `serialize_produto_with_image`/`GET /produtos`) pularem inteiramente o laço de fontes externas (Bing/Google/Zaffari/PreçoMelhor/Rissul) — só a imagem já salva localmente continua sendo servida. **Não afeta** cadastro de nome/marca (`fetch_product_from_*`, usado em rotas de registro automático) nem o botão "Buscar com IA" (fluxo separado, sempre exige clique humano numa miniatura antes de salvar qualquer coisa) — o toggle é especificamente sobre a busca automática e não-supervisionada de foto crua, que foi o que causou o incidente. `admin_buscar_imagem` retorna uma mensagem específica ("Busca de imagem online está desativada...") em vez do 404 genérico quando o toggle está desligado, pra quem usa o painel entender que é intencional, não que as fontes falharam. **Efeito colateral GLOBAL**: afeta TODOS os produtos, não só o problemático — útil pra pausar tudo na hora de um incidente, mas não é a ferramenta certa pra deixar ligado permanentemente (ver bloqueio por EAN abaixo, que é cirúrgico).

**2. Ferramenta de exclusão rápida por EAN** (Configurações → novo card "Excluir imagem de um produto pelo EAN"): campo de EAN + botão, chama a mesma rota `DELETE /deletar-imagem-produto/<codbar>` que o botão "Excluir imagem" do painel de detalhes já usava — só que sem precisar navegar até a Consulta Rápida e achar o produto primeiro. Pedido explícito do usuário: ter um jeito rápido de agir numa emergência como essa sem precisar caçar o produto na lista primeiro. Ganhou um checkbox "Bloquear busca automática... permanentemente" (marcado por padrão) — ver item 3.

### 3. Bloqueio permanente por EAN (`Produto.busca_imagem_bloqueada`) — adicionado depois da reincidência, é a mitigação de verdade

Descoberto testando a reincidência: só apagar o arquivo (mesmo dos dois diretórios) **não resolve nada sozinho** — o próprio auto-heal do sistema busca e salva a imagem de novo na consulta seguinte, e como o problema está na FONTE de dados (o mapeamento ruim EAN→imagem no PreçoMelhor não vai sumir sozinho), a mesma imagem ruim volta. O kill switch global (item 1) resolve isso, mas às custas de desligar a busca pra TODO produto — não dá pra deixar ligado pra sempre. A solução certa: um bloqueio **por produto**, permanente, independente de qual fonte trouxe o problema.

- **Nova coluna `Produto.busca_imagem_bloqueada`** (Boolean, default `False`, migration `d47bd29d1c4b_add_busca_imagem_bloqueada_to_produto.py`, mesmo padrão da migration de `tem_foto`: `server_default=false()`, sem índice porque não é usada pra ordenação, só consulta pontual por EAN).
- **`_pode_buscar_imagem_online(codbar)`**: combina as duas travas — kill switch global E o bloqueio por produto — só retorna `True` quando NENHUMA das duas está acionada. Usada em `obter_imagem_produto`; os outros dois call sites (`serialize_produto_with_image`, que já tem o objeto `produto` em mãos, e `admin_buscar_imagem`, que já busca o produto pra outra checagem) checam `produto.busca_imagem_bloqueada` direto, sem repetir a query.
- **Achado crítico testando o bloqueio pela primeira vez**: o EAN do incidente (`7898909864181`) **não tinha nenhuma linha na tabela `Produto`** neste banco local — `obter_imagem_produto` (a rota do terminal) nunca exigiu que o produto estivesse cadastrado pra tentar buscar imagem pra ele (documentado antes, na leva da fila de pendências). Sem uma linha `Produto`, não haveria onde gravar o bloqueio — a chamada de bloqueio simplesmente não faria nada, silenciosamente. Corrigido: `deletar_imagem_produto` com `?bloquear=true` agora **cria uma linha `Produto` mínima** (só `codbar` preenchido, mesmo padrão do cadastro manual "só EAN") quando ela não existe, exatamente pra garantir que o bloqueio sempre "pegue" de verdade, mesmo pra um EAN nunca cadastrado antes.
- **Contrato da rota**: `DELETE /deletar-imagem-produto/<codbar>?bloquear=true` — independente de ter encontrado arquivo pra apagar ou não, se `bloquear=true` o produto (criado se preciso) fica marcado. Resposta diferencia os casos: "Imagem deletada... e busca automática bloqueada", "Nenhuma imagem encontrada pra apagar, mas busca automática bloqueada", ou o 404 de sempre quando `bloquear=false` e nada foi achado.
- EAN `7898909864181` já foi bloqueado de verdade neste ambiente como parte do teste (não é hipotético) — confirmado que `GET /produto-imagem/7898909864181` volta a dar 404 sem tentar NENHUMA fonte externa (sem nenhum log de erro do Bing/Google/etc, diferente de antes). **Esse bloqueio existe só neste banco local — alguém com acesso ao `srv-mupa` precisa aplicar o mesmo em produção** (rodar a migration + chamar a rota com `bloquear=true`, ou usar a ferramenta no painel de produção depois que o deploy chegar lá).

### 4. Camada de segurança PROATIVA: `_imagem_e_segura` — classifica o CONTEÚDO antes de salvar, pra qualquer fonte, atual ou futura

Pedido explícito do usuário depois de resolver o incidente pontual: "conseguimos criar uma camada de segurança pra garantir que isso não aconteça mais?" — os itens 1-3 acima são todos REATIVOS (agem depois que já se sabe que um EAN específico é problemático). Faltava uma defesa que rejeitasse conteúdo impróprio **antes** de salvar, pra qualquer produto, de qualquer fonte, mesmo uma nunca vista antes.

- **`_imagem_e_segura(image_data)`**: manda os bytes da imagem pro **Gemini multimodal** (`gemini-2.5-flash-lite`, `genai_types.Part.from_bytes` — mesmo padrão já usado em `gerar_arte_publicitaria`/`compor_arte_vertical` pra mandar a foto do produto como referência, só que aqui pra CLASSIFICAR em vez de gerar) com um prompt pedindo pra responder `SEGURA` ou `IMPROPRIA`. Reaproveita a infraestrutura Gemini já configurada no sistema — não precisou de nenhuma chave/serviço novo (ex.: Google Cloud Vision SafeSearch Detection, que exigiria habilitar faturamento/API separada).
- **Ponto de checagem principal: dentro de `save_image_from_response`**, ANTES de escrever qualquer arquivo em disco. Essa função é o chokepoint por onde passam TODAS as fontes automáticas de imagem (Bing, Google, Zaffari, PreçoMelhor, Rissul) e também a seleção manual do picker "Buscar com IA" (`admin_definir_imagem_url`) — proteger só esse um ponto cobre tudo de uma vez, inclusive qualquer fonte nova que for adicionada no futuro (ninguém precisa lembrar de adicionar a checagem de novo).
- **Upload manual TAMBÉM passou a ser coberto** (`upload_imagem_produto` — botão "Enviar/Trocar imagem" — e o campo de imagem opcional de `admin_cadastrar_produto_manual`), numa leva seguinte pedida explicitamente pelo usuário — reverte a decisão original (documentada acima como "categoria de risco diferente, upload é um humano escolhendo o arquivo"). Na prática um upload manual pode ser feito às pressas, sem olhar direito a miniatura, então vale a mesma proteção. As duas rotas leem os bytes do arquivo (`file.read()`, não mais `file.save()` direto) e chamam `_imagem_e_segura` antes de gravar em `IMAGES_FOLDER`; se reprovada, chamam `_quarentenar_imagem(dados, codbar, origem='upload_manual')` em vez de salvar. Diferença de comportamento entre as duas rotas quando a imagem é reprovada: `upload_imagem_produto` responde `422` (nada mais acontece); `admin_cadastrar_produto_manual` responde `201` normalmente e **cria o produto do mesmo jeito** (com a descrição, se enviada) — só a imagem some pra quarentena, indicado na resposta por `imagem_quarentenada: true`/`imagem_salva: false`, já que cadastrar o produto e aceitar a foto são decisões independentes. Testado de ponta a ponta com EANs descartáveis: caminho seguro (classificação REAL do Gemini, foto de referência Coca-Cola) confirmado salvando sem regressão depois da troca de `file.save()` pra `read()+write()`; caminho de rejeição testado com `_imagem_e_segura` mockada (evita gastar uma reprovação real/conteúdo impróprio de novo, já validado antes) — confirmado que nenhum arquivo vai pra `IMAGES_FOLDER`, o produto é criado e bloqueado, e a linha `ImagemQuarentena` é criada corretamente nas duas rotas.
- **Se a imagem for rejeitada**: `save_image_from_response` retorna `(mensagem, 422)` em vez de `200` — os 5 `buscar_e_salvar_imagem_*` e o picker de IA já tratam qualquer status ≠ 200 como "essa fonte não achou nada" (código deles não precisou mudar nem uma linha) — a cadeia automaticamente tenta a próxima fonte, e se todas falharem/forem rejeitadas, o produto cai na fila de pendências normal (`_registrar_busca_imagem(codbar, False, ...)`). **Atualizado numa leva seguinte** (ver "Quarentena de imagens" abaixo): a imagem rejeitada não é mais descartada — vai pra uma pasta de quarentena + fila de revisão humana, embora `save_image_from_response`/`IMAGES_FOLDER`/`PROCESSED_IMAGES_FOLDER` nunca a recebam, então pro resto do sistema (terminal, painel, catálogo) o comportamento observável continua sendo "essa fonte não achou nada".
- **Falha aberta deliberada**: se a classificação der erro (sem `GEMINI_API_KEY` configurada, rede fora, cota do Gemini esgotada), `_imagem_e_segura` retorna `True` (permite salvar) em vez de travar a busca de imagem inteira do sistema por causa de uma falha de classificação. Aceito conscientemente: a prioridade nº1 dessa camada é pegar o caso comum (fonte disponível, classificação funcionando), não virar um novo ponto único de falha que derruba a busca de imagem de todo o catálogo se o Gemini cair.
- **Testado com as duas imagens reais do incidente**: a imagem pornográfica confirmada (mesma URL do PreçoMelhor, baixada de novo direto pra teste) classificada corretamente como `IMPROPRIA`; uma foto de produto normal (Coca-Cola, mesmo EAN de referência usado o resto da sessão) classificada corretamente como `SEGURA`, sem falso positivo.

### 5. Auditoria retroativa + quarentena com revisão humana (pedido do usuário em duas rodadas)

Depois do filtro proativo (item 4) resolver o problema PRA FRENTE, faltavam duas coisas: (a) checar se alguma das imagens **já salvas** no catálogo (baixadas antes do filtro existir) também tinha esse problema, e (b) o que fazer de fato com uma imagem rejeitada, já que só descartar silenciosamente (comportamento original do item 4) não deixava rastro nenhum pra auditoria/evidência nem dava chance de corrigir um falso positivo do classificador.

**Pedido inicial do usuário — "consegue fazer scraping desse site pra achar mais imagens assim?" — RECUSADO**: o usuário pediu pra varrer o site do PreçoMelhor em massa procurando mais imagens impróprias e baixar tudo numa pasta. Recusei fazer isso — três motivos: (1) uma varredura "procurando mais imagens assim" pode trazer qualquer coisa, incluindo conteúdo muito mais grave sem nenhum filtro prévio pra saber o que vai chegar; (2) acumular esse tipo de conteúdo numa pasta é exatamente o risco que estávamos tentando evitar, só que concentrado; (3) scraping em massa no site de um terceiro tem problemas próprios (termos de uso, Cloudflare) independente do conteúdo. Em vez disso, propus (e o usuário aceitou) auditar só as imagens que **já são nossas** (já baixadas, já no disco) — sem buscar nada novo na internet.

**Auditoria retroativa**: rodei o classificador (`_imagem_e_segura`) em todas as ~220 imagens já salvas em `IMAGES_FOLDER` neste ambiente de dev. Achado: **1 de 220 imprópria** — um arquivo órfão de teste com EAN inválido (`99999999999999999`, 17 dígitos, claramente não um código de barras real, não um produto do catálogo). As outras 219 passaram limpas. Essa primeira rodada ainda usava o comportamento antigo (apagar direto + bloquear, sem quarentena) — a pasta de quarentena só foi criada na rodada seguinte.

**Pedido seguinte do usuário — script pra rodar no `srv-mupa` + fluxo de quarentena**: como não tenho acesso a produção, preparei `scripts/auditoria_seguranca_imagens.py` (comitado no repo, roda em qualquer ambiente que tenha o `app.py` — dev ou produção) fazendo a mesma varredura. E, junto disso, o usuário pediu pra mudar o comportamento de rejeição: em vez de descartar (dev) ou apagar+bloquear direto (script antigo), agora toda imagem rejeitada vai pra uma **fila de quarentena com revisão humana**.

- **`QUARENTENA_FOLDER = 'quarentena_imagens'`** — pasta na raiz do projeto, **deliberadamente fora de `static/`** (que o Flask serve publicamente sem autenticação nenhuma) — uma imagem em revisão não pode ficar acessível por URL direta só por estar "só" numa subpasta. Adicionada ao `.gitignore` (dado local sensível, mesmo tratamento de `static/`/`instance/`).
- **`ImagemQuarentena`** (novo model + migration `840efabc3897_add_imagem_quarentena_table.py`): `codbar`, `arquivo` (nome do arquivo em `QUARENTENA_FOLDER`, vira `None` depois de revisado), `origem` (de qual fonte veio — bing/google/zaffari/precomelhor/rissul/ia/cosmos/auditoria — **não passa por `rotuloFonte`/`FONTES_OCULTAS_NO_PAINEL` nessa página**, ao contrário do resto do painel: essa é justamente a ferramenta de investigar incidentes, esconder a fonte aqui seria contraproducente), `criado_em`, `decisao` (`None`=pendente / `'confirmada'` / `'liberada'`), `revisado_em`.
- **`_quarentenar_imagem(image_data, codbar, origem)`**: chamada de dentro de `save_image_from_response` quando `_imagem_e_segura` rejeita — salva o arquivo em `QUARENTENA_FOLDER` (nome com timestamp, evita colisão se o mesmo EAN for rejeitado mais de uma vez), cria a linha `ImagemQuarentena`, e **já bloqueia o EAN na hora** (`Produto.busca_imagem_bloqueada = True`, criando um `Produto` mínimo se o EAN ainda não existir cadastrado — mesmo gap e mesma correção do incidente original, onde o EAN nem tinha cadastro). Erra pro lado de proteger o cliente por padrão: o bloqueio é imediato, a revisão humana decide DEPOIS se era falso positivo.
- **4 rotas novas, todas autenticadas**:
  - `GET /admin/quarentena` — lista paginada, filtro por `status` (pendente/confirmada/liberada/todos).
  - `GET /admin/quarentena-imagem/<id>` — serve o ARQUIVO da imagem. Só existe pra poder mostrar a miniatura no painel sem expor a pasta publicamente. **Detalhe técnico real, pego testando**: a implementação inicial usava `send_file(caminho, ...)` direto do caminho em disco — no Windows, isso deixa o handle do arquivo aberto por um instante além do fim da resposta, e como o fluxo normal é "ver a imagem" seguido logo depois por "confirmar" (que apaga o arquivo), isso causava um `WinError 32` real ("arquivo já está sendo usado por outro processo") quando as duas chamadas aconteciam em sequência rápida. Corrigido lendo o arquivo pra memória (`io.BytesIO`) antes de servir — o handle em disco fecha assim que a leitura termina, antes da resposta HTTP nem começar a ser montada.
  - `POST /admin/quarentena/<id>/confirmar` — humano confirma que é mesmo imprópria: apaga o arquivo físico (não faz sentido guardar o conteúdo indefinidamente só pelo registro existir), mantém o bloqueio do EAN (já estava ativo desde a rejeição).
  - `POST /admin/quarentena/<id>/liberar` — humano decide que foi falso positivo do classificador: move o arquivo de volta pra `IMAGES_FOLDER` + reprocessa (remoção de fundo, mesmo código de `save_image_from_response`) pra `PROCESSED_IMAGES_FOLDER`, desbloqueia o EAN, marca `tem_foto=True`. **Não passa pelo classificador de novo** — decisão humana aqui é definitiva, não faz sentido rejeitar automaticamente algo que um humano acabou de revisar e aprovar.
- **Aba "Quarentena" no painel** (`configuracoes.html`, entre Histórico e WhatsApp na barra lateral, badge com contagem de pendentes): cards em grade, **miniatura borrada por padrão** (`filter: blur(22px)`, botão "👁 Revelar" por cima) — like a UI de moderação de conteúdo, não expõe a imagem sem um clique deliberado de quem está revisando. Como a rota de imagem exige JWT, um `<img src="...">` direto não funcionaria (o navegador não manda o header `Authorization` em tags `<img>`) — o "Revelar" faz um `fetch()` autenticado, converte a resposta em blob URL, e só então cria o `<img>` (então a imagem nem é baixada pro navegador antes do clique).
- **`scripts/auditoria_seguranca_imagens.py`**: standalone, reaproveita `_imagem_e_segura`/`_quarentenar_imagem` do próprio `app.py` (mesmo ambiente, mesmo banco) — varre `IMAGES_FOLDER` inteiro, e pra cada imprópria: move pra quarentena (copia bytes + registra + bloqueia) e SÓ DEPOIS remove dos diretórios normais (nessa ordem, pra nunca ficar sem nenhuma cópia do arquivo se algo falhar no meio). Pensado pra rodar tanto aqui quanto no `srv-mupa` — nesse último, o catálogo de imagens é bem maior que os ~220 arquivos daqui, então cada rodada custa mais chamadas reais ao Gemini (uma por imagem) e pode levar bastante tempo; recomendado rodar em background e acompanhar o log.
- Testado de ponta a ponta (script de teste isolado, EANs descartáveis criados/removidos na própria sessão de teste): `_quarentenar_imagem` com a imagem real do incidente — arquivo salvo em `QUARENTENA_FOLDER`, linha criada, `Produto` criado do zero e bloqueado; `GET /admin/quarentena` listou a entrada; `GET /admin/quarentena-imagem/<id>` serviu os bytes corretos; `POST .../confirmar` apagou o arquivo e manteve o bloqueio; num segundo teste com uma foto legítima (Coca-Cola) inserida manualmente na quarentena simulando um falso positivo, `POST .../liberar` restaurou a imagem corretamente em `IMAGES_FOLDER`/`PROCESSED_IMAGES_FOLDER` (confirmado visualmente — o arquivo processado é a mesma garrafa de Coca-Cola de sempre), desbloqueou o EAN e marcou `tem_foto=True`. Testado também ao vivo no navegador: aba renderiza, badge de pendentes na barra lateral aparece, "Revelar" busca e desborra a miniatura corretamente, botões "Confirmar"/"Liberar" disparam o `confirm()` de segurança antes de agir.

### 6. Verificação de correspondência imagem × descrição (`_imagem_corresponde_descricao`) — pega imagem SEGURA mas ERRADA

Pedido do usuário: "quero adicionar mais uma verificação antes de enviar a imagem para a url pública... uma OCR que verifica se a imagem do produto corresponde a descrição. Pra isso, precisa ter o cadastro do produto." Motivação direta do incidente do PreçoMelhor (ver acima) — `_imagem_e_segura` só pega conteúdo IMPRÓPRIO; nunca pegaria (nem deveria, não é o trabalho dela) uma imagem perfeitamente segura mas do produto ERRADO (ex.: a foto de um sabonete salva pra um EAN de refrigerante, porque a fonte externa mapeou mal). Faltava uma camada checando IDENTIDADE, não só impropriedade.

- **Por que Gemini multimodal em vez de OCR literal (Tesseract ou similar)**: o pedido do usuário usa a palavra "OCR", mas a necessidade real é "a imagem bate com a descrição", não "extrair o texto da imagem". Optei por reaproveitar o Gemini multimodal (mesma infraestrutura de `_imagem_e_segura`, mesmo `Part.from_bytes`) em vez de instalar uma lib de OCR dedicada, por três motivos: (1) o modelo já lê texto impresso na embalagem como parte de entender a cena — cumpre a função de "OCR" sem precisar de uma segunda ferramenta; (2) além do texto, ele julga por contexto visual (formato, cor, categoria) mesmo quando o texto não é 100% legível na foto — mais robusto que OCR puro, que só extrai caracteres sem julgar correspondência semântica (ex.: "Refrigerante Cola 2L" bate com "Coca-Cola 2 Litros" mesmo sem nenhuma palavra idêntica); (3) evita instalar um binário externo nesta máquina Windows já documentada como "sem reloader confiável" (Tesseract não é só `pip install`, precisa do executável no sistema, `PATH`, etc.).
- **`_imagem_corresponde_descricao(image_data, descricao, marca=None)`**: manda a imagem + `f'{descricao} (marca: {marca})'` pro Gemini (`gemini-2.5-flash-lite`, mesmo modelo de `_imagem_e_segura`), pede pra responder só `CORRESPONDE` ou `NAO_CORRESPONDE`. Falha aberta deliberada, mesmo padrão de `_imagem_e_segura`: erro de classificação (sem chave, rede, cota) libera a imagem em vez de travar a busca inteira — essa camada é reforço de qualidade, não a única linha de defesa.
- **"Precisa ter o cadastro do produto"**: só roda quando `Produto.description` já está preenchida — sem uma descrição real pra comparar, não há contra o que verificar (por isso a checagem lê `Produto.query.filter_by(codbar=codbar).first()` antes de decidir se roda ou não). Um EAN sem cadastro, ou cadastrado só com o EAN (sem description), passa direto sem essa checagem — mesmo comportamento de antes.
- **Onde entra**: dentro de `save_image_from_response` (chokepoint de sempre — cobre as 7 fontes automáticas + o picker "Buscar com IA", `admin_definir_imagem_url`), DEPOIS da checagem de impropriedade (não faz sentido gastar uma chamada extra ao Gemini numa imagem que já vai pra quarentena por outro motivo). Também duplicada nas 2 rotas de upload manual que NÃO passam por `save_image_from_response` (`upload_imagem_produto`/"Enviar-Trocar imagem" e o campo de imagem de `admin_cadastrar_produto_manual`) — mesmo padrão de duplicação já usado pra `_imagem_e_segura` nesses dois pontos (documentado no item 4 acima: "upload manual pode ser feito às pressas, sem olhar direito a miniatura"). No cadastro manual, a comparação usa a `description` que veio na PRÓPRIA requisição (checa consistência do que o humano acabou de digitar+anexar juntos), não uma já salva no banco.
- **Kill switch dedicado** (`VERIFICACAO_DESCRICAO_ATIVA`, Config, default `'true'`, `_verificacao_descricao_ativa()`, toggle em Configurações → Flags de Funcionamento): mesma filosofia dos outros kill switches deste projeto — se o classificador começar a rejeitar demais (ex.: descrições do catálogo abreviadas demais, tipo "REFRIG COCA 600ML", pro Gemini reconhecer com confiança), dá pra desligar na hora sem deploy, sem precisar desligar a busca de imagem nem `_imagem_e_segura`.

### Popup de detalhes na Quarentena — link da fonte + todas as formas de consertar, num clique só

Pedido do usuário: "adicionar detalhe, abrir um popup que vai abrir o link que baixou a imagem e tudo de possibilidades para arrumar quando a imagem está errada... lembrando sempre que é uma pessoa que vai realizar a auditoria, quanto mais rápido melhor". Decisão: reaproveitar esse padrão já estabelecido em vez de inventar um novo — mais rápido de construir, mais consistente pro usuário que já conhece esse popup de outras abas, e menos CSS novo.

- **`ImagemQuarentena.url_origem`** (nova coluna, `String(1000)`, nullable, migration `b7d3e0f9a2c1`): a URL de onde a imagem foi baixada. Falha (nenhuma fonte achou nada, ou a nova imagem caiu em quarentena de novo por outro motivo): EAN fica desbloqueado mas a entrada original continua pendente, toast explica o resultado, popup continua aberto. #### Popup da Quarentena virou centralizado, com navegação anterior/próximo (pedido do usuário logo em seguida)

Pedido: "Vamos mudar pra popup no centro da tela podendo percorrer próximo, botões na lateral" — o popup de detalhes acima (item anterior) nasceu deslizando pela lateral direita, reaproveitando `.detail-panel`/`.detail-panel-backdrop` (o mesmo padrão de Consulta Rápida/Histórico). Trocado especificamente pra esse popup (os outros dois painéis continuam deslizando pela lateral, sem mudança) por um popup **centralizado na tela**, com **botões de seta fixos nas bordas esquerda/direita do VIEWPORT** (não do popup) pra avançar/voltar sem fechar — direto na linha do "quanto mais rápido melhor" da revisão em fila já estabelecido nesta mesma seção.

- **HTML reestruturado**: o backdrop deixou de ser um elemento IRMÃO do popup (`.detail-panel-backdrop` cobria a tela toda, mas o popup em si era outro `<div>` posicionado independente pela lateral) e passou a ser o **pai** do popup, igual ao padrão já usado no modal de cadastro (`.modal-overlay`/`.modal-panel`) — `#quarentena-detail-backdrop` agora é um flex container centralizando `#quarentena-detail-panel` como filho, com os dois botões de navegação (`#quarentena-detail-prev`/`#quarentena-detail-next`) como outros filhos diretos do mesmo backdrop (fixos no viewport via `position:fixed`, então continuam nas bordas da tela não importa o tamanho do popup).
- **CSS novo** (`.quarentena-detail-backdrop`/`.quarentena-detail-modal`/`.quarentena-nav-btn`), **não** reaproveitando `.detail-panel`/`.modal-overlay` diretamente — só peguei emprestado o PADRÃO (fade+scale ao abrir, clique fora fecha, Esc fecha), não as classes em si, porque este popup tem geometria (centralizado, largura maior — 560px em vez de 440/480px, já que agora tem uma imagem 16:9 acima do conteúdo em vez de ao lado) e comportamento (navegação) diferentes o bastante dos outros dois pra não valer a pena forçar reaproveitamento de classe.
  - **Cuidado de especificidade CSS que passou batido na primeira tentativa**: `.quarentena-detail-modal` sozinha (uma classe) tem a MESMA especificidade que `.modal-panel` (também definida no HTML do popup, pro botão de fechar/scroll interno funcionar igual ao resto) — como `.modal-panel` vem DEPOIS no arquivo, venceria o empate e sobrescreveria `max-width`/`overflow-y`/`margin` de volta pros valores do popup de cadastro (480px em vez dos 560px pretendidos). Corrigido escopando pelo ID (`#quarentena-detail-panel.quarentena-detail-modal`), que tem especificidade maior que qualquer combinação de classes, garantindo as propriedades certas independente da ordem das regras no arquivo.

Só navega dentro da PÁGINA de paginação atual (o conjunto em memória); nos extremos (primeiro/último item da página), o botão correspondente fica `disabled` em vez de dar erro ou dar a volta — `openQuarentenaDetail` recalcula `disabled` dos dois botões toda vez que abre um item, junto com um indicador "N de M" no cabeçalho do popup.
- **Atalho de teclado** (`ArrowLeft`/`ArrowRight`) navega junto com os botões — deixa o revisor folhear a fila só com o teclado, sem precisar mirar o mouse num botão pequeno repetidamente; `Escape` continua fechando, agora checando a classe `.show` do backdrop (não mais `.open` do painel, que deixou de existir nesse popup).

#### "Liberar" na Quarentena também elimina outras entradas pendentes do MESMO EAN (pedido do usuário: "tanto faz o motivo")

Achado do próprio uso do sistema: com várias fontes/tentativas diferentes rejeitando a mesma imagem (ou imagens diferentes) do mesmo produto, um único EAN podia acumular **várias entradas pendentes na fila de Quarentena ao mesmo tempo** (ex.: uma rejeitada por `_imagem_e_segura`, outra por `_imagem_corresponde_descricao`, outra por política de fonte — `motivo`s diferentes, mas todas sobre o mesmo produto). Quando um humano libera UMA delas (decide que a foto está certa, aprova como foto oficial), as outras entradas pendentes daquele mesmo EAN viram ruído puro — o barcode já tem uma foto boa aprovada, revisar as demais uma por uma não agrega nada.

- **`_eliminar_duplicatas_pendentes(codbar, excluir_id)`** (helper novo, ao lado de `_quarentenar_imagem`): apaga arquivo + linha do banco de toda `ImagemQuarentena` com o mesmo `codbar`, `decisao IS NULL` (ainda pendente de verdade) e `id` diferente da que acabou de ser liberada. **Não filtra por `motivo`** de propósito — pedido explícito do usuário ("tanto faz o motivo") — uma rejeição por conteúdo impróprio, por política de fonte ou por descrição incompatível pro mesmo EAN são igualmente irrelevantes depois que uma foto dele já foi aprovada.
- **Só entradas PENDENTES são tocadas** (`decisao IS NULL`) — uma entrada já `'confirmada'` ou `'liberada'` antes é histórico de uma decisão humana já tomada sobre aquela imagem específica, e fica intocada; a limpeza automática é só pra evitar trabalho duplicado numa revisão que ainda não aconteceu, não pra apagar registro de revisões já feitas.
- **Chamado de dentro de `admin_quarentena_liberar`**, na mesma transação/commit da liberação principal — atômico (se a liberação falhar, as duplicatas também não são tocadas). A resposta da rota (`data.message`, já usada pelo toast do frontend sem nenhuma mudança de código) passa a citar quantas duplicatas foram removidas, quando aplicável — o frontend não precisou de nenhuma alteração pra mostrar isso, já reaproveita a mensagem que vem do backend.

#### Ampliação seguinte, pedido do usuário mostrando um caso real em produção: deduplicar na ORIGEM + limpar dupes em QUALQUER caminho de resolução, não só "Liberar"

Usuário mandou um print da Quarentena em produção mostrando **3 entradas pendentes idênticas** do mesmo EAN (`7896304103393`), criadas com **menos de 1.2s de diferença** entre elas — todas `origem='serper'` + `motivo='revisao_obrigatoria_fonte'`. Investigado ao vivo via Claude in Chrome (acessando o painel real em produção, `srv2000031.hstgr.cloud:5050`, mesmo servidor de `2.25.239.153` por trás de um hostname diferente): `ultimaQuarentenaData` confirmou os 3 registros (ids 60/61/62) com timestamps `12:07:08.727`, `12:07:09.410`, `12:07:09.885`.

**Causa raiz real**: com uma fonte marcada "revisão obrigatória" (`_fonte_exige_revisao`, ver seção "Toggle individual por fonte de imagem"), **TODA** imagem que ela encontra vai pra quarentena — não é uma classificação de conteúdo, é uma política cega. Cada chamada independente da cadeia de busca pro mesmo EAN (vários terminais de lojas diferentes consultando o mesmo produto sem foto, quase ao mesmo tempo) faz sua própria tentativa, encontra a mesma imagem via Serper (busca determinística pro mesmo EAN) e cria sua própria linha de quarentena — sem nenhuma deduplicação, três chamadas quase simultâneas viram três linhas idênticas.

Usuário: "quando eu trocar a imagem do produto, não vai apagar as outras... Ou então o sistema já deve unificar quando o ean repetir" — os DOIS pedidos foram implementados, atacando o problema dos dois lados:

**1. Deduplicação na ORIGEM, por CONTEÚDO (não só por EAN)** — `_quarentenar_imagem` agora compara os bytes da imagem chegando contra o arquivo de toda entrada AINDA PENDENTE do mesmo EAN; se algum bater byte-a-byte, a nova é descartada (nem escreve arquivo, nem cria linha) — só loga que era duplicata. **Deliberadamente por conteúdo, não só por EAN**: um EAN com duas rejeições pendentes de imagens GENUINAMENTE diferentes (ex.: uma fonte trouxe uma foto errada, outra trouxe conteúdo impróprio) continua gerando duas linhas — cada imagem diferente merece revisão própria; só a repetição EXATA da mesma imagem é que é ruído.

**2. Limpeza de duplicatas em QUALQUER caminho que resolva o EAN com uma foto boa**, não só "Liberar" — `_eliminar_duplicatas_pendentes(codbar, excluir_id=None)` (assinatura generalizada, `excluir_id` agora opcional): sem exclusão, apaga TODAS as pendentes do EAN. Chamado a partir de:
  - **`save_image_from_response`** (chokepoint que cobre TODAS as fontes automáticas + "Buscar com IA" via `admin_definir_imagem_url`) — dentro do caminho de SUCESSO (não do de rejeição), logo depois de `_marcar_tem_foto`. Isso automaticamente cobre também "Tentar buscar de novo" (`admin_quarentena_tentar_novamente`), já que essa rota chama `admin_buscar_imagem` → `buscar_e_salvar_imagem_*` → `save_image_from_response` por baixo.
  - **`upload_imagem_produto`** ("Enviar/Trocar imagem") — rota separada que NÃO passa por `save_image_from_response` (tem seu próprio salvamento direto), precisou do mesmo hook manualmente, no mesmo ponto (depois de `_marcar_tem_foto`, antes do commit).

**Bug real de passagem, achado E corrigido implementando o item 2 (antes de existir em produção)**: como `_eliminar_duplicatas_pendentes` agora roda DENTRO de `admin_buscar_imagem` (chamado por `admin_quarentena_tentar_novamente`), ela pode apagar a PRÓPRIA entrada que `admin_quarentena_tentar_novamente` estava processando — a entrada some do banco ANTES da rota terminar seu próprio código de fechamento manual (`entrada.arquivo = None; entrada.decisao = 'confirmada'; db.session.commit()`), que tentaria dar UPDATE numa linha que não existe mais (erro real de SQLAlchemy, `StaleDataError`/objeto obsoleto). Corrigido reconsultando a entrada pelo id DEPOIS de `admin_buscar_imagem` retornar sucesso, em vez de reaproveitar a referência em memória — se ela já sumiu (caso comum agora), não há mais nada a fazer; só faz o fechamento manual se ela sobreviveu por algum motivo (ex.: arquivo já não existia no disco quando a limpeza rodou). Testado explicitamente os dois ramos (com `admin_buscar_imagem` mockado): sucesso com a limpeza automática já tendo apagado a entrada (sem exceção, resposta 200 normal) e sucesso SEM a limpeza ter rodado (fechamento manual de fallback confirmado funcionando, `decisao='confirmada'`).

Testado de ponta a ponta: (1) a MESMA imagem enviada 3x seguidas pro mesmo EAN via `_quarentenar_imagem` direto criou só 1 linha; uma imagem DIFERENTE pro mesmo EAN logo depois criou uma 2ª linha própria (confirma que não é uma deduplicação cega por EAN); (2) 2 entradas pendentes de motivos diferentes pro mesmo EAN, seguidas de um upload manual bem-sucedido (`POST /upload-imagem-produto/<ean>`, imagem sintética via canvas no navegador) — as duas somem (`GET /admin/quarentena?codbar=...&status=todos` volta com `total: 0`), sem erro no log do servidor; (3) a colisão do "Tentar buscar de novo" testada isoladamente nos dois ramos, como descrito acima. Dados de teste removidos depois.

Pedido explícito do usuário: "a request `/produto-imagem/` deve sempre disponibilizar a imagem da pasta `/static/processed_images`". ### Leva final desse mesmo assunto: parar de duplicar a imagem em disco — só `PROCESSED_IMAGES_FOLDER` existe

Depois das correções acima (sempre SERVIR a processada), o usuário pediu o passo seguinte: parar de GRAVAR a crua também — "não devemos ter a mesma imagem em dois lugares, somente no caminho que disponibiliza a url da imagem". Isso é mais fundo que as correções anteriores: aquelas só mudavam qual pasta a URL apontava; esta muda o que é salvo em disco.

**Conflito real que exigiu confirmação do usuário antes de mexer**: a geração de arte publicitária (`gerar_arte_publicitaria`) sempre usou a foto CRUA como referência pra IA (produto com fundo, contexto completo) — nunca a versão já sem fundo. Eliminar a cópia crua significa que a IA passa a ver a versão sem fundo como referência. Perguntei antes de decidir sozinho; o usuário confirmou explicitamente que prefere eliminar a duplicação mesmo assim (ainda não comparado visualmente se muda a qualidade da arte gerada — vale acompanhar nas próximas gerações).

- **`save_image_from_response`** (o chokepoint de sempre): não escreve mais nada em `IMAGES_FOLDER`. Abre a imagem direto dos bytes em memória (`Image.open(io.BytesIO(image_data))`), processa, e só o resultado (`PROCESSED_IMAGES_FOLDER/<codbar>.png`) vai pro disco.
- **`save_image_with_background_removal`**: antes, com `REMBG_ENABLED=false`, simplesmente **não salvava nada** (só logava um aviso) — fazia sentido quando ainda existia a cópia crua como rede de segurança. Sem essa cópia crua, isso significaria "imagem não salva em lugar nenhum" sempre que o rembg estivesse desativado. Corrigido: com `REMBG_ENABLED=false`, salva a imagem **sem remover o fundo** em vez de não salvar nada — o toggle passa a controlar só a remoção de fundo, não mais "salva ou não salva".
- **Todo ponto que ESCREVIA em `IMAGES_FOLDER` direto** também mudou pra ir só via remoção de fundo → `PROCESSED_IMAGES_FOLDER`: `upload_imagem_produto` (Enviar/Trocar imagem), `admin_cadastrar_produto_manual` (campo de imagem do cadastro manual), e `gerar_arte_publica` (rota pública `POST /produto-imagem/<codbar>/gerar-arte`, usada pelo app quando a foto vem de uma integração própria do cliente).
  - **Achado de bug de passagem em `gerar_arte_publica`**: essa rota escrevia os bytes recebidos direto em disco, **sem nunca passar por `_imagem_e_segura`** — um buraco real no filtro de conteúdo impróprio (ver seção do incidente), só descoberto ao consolidar esse ponto pra reaproveitar `save_image_from_response`. Agora passa pelo mesmo chokepoint de segurança que todas as outras fontes. Preserva o comportamento idempotente de antes (só salva se o produto AINDA não tiver imagem — não sobrescreve uma imagem boa já existente com o que vier no corpo desta chamada específica).
- **Todo ponto que LIA de `IMAGES_FOLDER` pra decidir "já tem imagem" ou montar a URL servida** trocou pra `PROCESSED_IMAGES_FOLDER` como fonte primária: `_registrar_busca_imagem`, `obter_imagem_produto` (inclusive o `img_path` que alimenta `_enfileirar_geracao_arte` — a arte agora usa a processada como referência, não mais a crua), `serialize_produto_with_image`, `admin_buscar_imagem`, `admin_gerar_arte`, `admin_estatisticas`, `admin_produtos_com_foto`, `admin_consulta_simples` (as 3 buscas: EAN exato/descrição/marca), `admin_historico_buscas` (filtro "já tem foto agora"), `_estatisticas_gerais` (resumo diário), `listar_imagens`, e os dois gatilhos de auto-download de thumbnail externo (`register_product_in_database`/cadastro via Cosmos).

- **Compatibilidade com arquivos antigos, não mudado**: `deletar_imagem_produto` continua varrendo as DUAS pastas (função de limpeza, sem custo checar as duas); `_listar_imagens_orfas` agora escaneia as duas pastas e prioriza a processada quando existem as duas; `admin_consulta_produtos` mantém um fallback pra crua na hora de montar a miniatura, só pro caso raro de sobrar um arquivo órfão só na pasta antiga. Nenhum arquivo já existente em `IMAGES_FOLDER` de antes dessa mudança foi apagado — a limpeza da duplicação já acumulada (crua + processada dos produtos salvos antes desta correção) fica pra uma leva separada, se for pedida.

### Hierarquia tipográfica: marca em destaque + resto do nome pequeno/leve

Pedido explícito do usuário com valores de referência (~80px peso 400 pra marca, ~40px peso 200 pro resto — escalados proporcionalmente à altura da imagem, não em pixels fixos, como todo o resto do texto). A fonte variável Montserrat já tem os pesos nomeados certos: `Regular` ≈ peso 400, `ExtraLight` ≈ peso 200 (confirmado via `font.get_variation_names()`).

- `_separar_marca_do_nome(nome, marca)`: separa a marca do resto do nome (remove o prefixo se o nome já começar pela marca, ex. `nome='Coca-Cola Sabor Original'` + `marca='Coca-Cola'` → `('Coca-Cola', 'Sabor Original')`); se não bater o prefixo, mantém o nome inteiro como "resto" mesmo assim (prefere uma pequena redundância a perder o destaque da marca).
- Quando há marca identificável: marca desenhada grande (peso Regular), resto do nome + quantidade juntos numa fonte ~metade do tamanho (peso ExtraLight) — a quantidade não precisa mais de uma linha garantida em fonte grande nesse tamanho reduzido, cabe tranquilamente junto com o resto.
- Sem marca identificável: usa a **1ª palavra do nome** como destaque (mesma regra de peso/tamanho da marca de verdade) em vez de cair pro estilo antigo (nome inteiro grande e uniforme, sem hierarquia). Mudado depois que um requeijão Vigor saiu com "Requeijão cremoso tradicional 400G" tudo do mesmo tamanho porque nenhuma fonte (banco/Cosmos/OFF/Zaffari/Google/AI) resolveu a marca daquela vez — não é a marca de verdade, mas garante que SEMPRE haja hierarquia tipográfica, nunca um bloco de texto uniforme. Só cai pro `None` (nome inteiro, sem split) quando o nome é uma única palavra sem "resto" possível.
- Testado com marca de 1 palavra (Coca-Cola), 3 palavras (Dove Men Care) e sem marca identificável (Requeijão Vigor, usando "Requeijão" como palavra de destaque) — quebra de linha e proporção funcionam bem nos três casos.

Também reduzida a fonte da headline em 40% (pedido do usuário) — o painel esquerdo ficou visivelmente mais enxuto (marca + resto + headline, tudo mais compacto), sobrando bem mais espaço vazio na faixa inferior pro card de preço.

### Bullets de benefício: cápsula translúcida + ancorados na BASE (não mais centralizados)

Pedido do usuário pra "baixar um pouco mais" o bloco de bullets expôs um problema que antes passava despercebido: o bloco de bullets é sempre encostado na borda direita (`icone_x = int(width * 0.965) - diametro_icone`), então o texto (que cresce pra ESQUERDA do ícone, `alinhar_direita=True`) cai onde quer que a garrafa/produto esteja naquela altura — quando centralizado verticalmente, o texto caía direto em cima do rótulo do produto, ilegível mesmo com a sombra (`_desenhar_texto_com_sombra` sozinha não é suficiente contra um fundo com textura/contraste, só contra fundo liso).

Duas correções, na ordem em que foram pedidas:
1. **Cápsula translúcida** em `_desenhar_bullet_beneficio`: quando `alinhar_direita=True` (sempre o caso do lado direito, sobre a foto), desenha uma cápsula semitransparente (`fill=(20,20,24,140)`, `rounded_rectangle` com raio = metade da altura) atrás do grupo ícone+texto, ANTES do ícone e do texto. Garante legibilidade em qualquer parte da cena, inclusive sobre o rótulo do produto — mesmo recurso usado em peças publicitárias reais (badge/tarja atrás de texto sobre foto), não é só um workaround. Não usar essa cápsula do lado não-`alinhar_direita` (painel esquerdo) — lá o fundo já é sólido, cápsula seria redundante.
2. **Ancorado na base em vez de centralizado**: usuário pediu explicitamente ("os benefícios fiquem na base, com uma margem pra não encostar na base") — `bloco_y` deixou de ser `(height - altura_bloco) / 2 + offset` (cálculo a partir do centro) e passou a ser `height - margem_inferior - altura_bloco` (`margem_inferior = int(height * 0.08)`), ancorado a partir da borda inferior. Fica na mesma faixa vertical inferior onde a cena costuma ter menos elementos importantes (chão/mesa/gelo), e não compete mais com a parte superior do produto.

### Risco residual conhecido (não totalmente resolvido)

O modelo de imagem às vezes **recria o texto já impresso na própria embalagem** com erro de grafia (ex.: "HARPIC" virou "HARIC", "PASTILHA" virou "PASTITILA") — isso não é a IA "escrevendo" texto novo (proibido e evitado via PIL), é ela **redesenhando** a embalagem de referência de forma levemente imperfeita. Diferente do nome/headline (que são 100% PIL), esse texto faz parte da foto do produto em si e não tem uma solução equivalente ainda. Se voltar a acontecer com frequência, considerar: reforçar ainda mais a instrução de fidelidade, ou testar `gemini-2.5-flash-image` com temperatura mais baixa.

### Corrupção de encoding no catálogo (mojibake, dados irreversíveis)

Parte do catálogo importado tem `description`/`marca` corrompidos — **dois tipos diferentes**, ambos precisam ser checados (`_texto_corrompido`):
1. Caractere de substituição `U+FFFD` (`�`) — corrupção "limpa", já virou perda de dado.
2. Bytes de controle C1 soltos (`U+0080`–`U+009F`, ex.: `\x94`) — mojibake de UTF-8 lido como Latin-1/Windows-1252, sem virar `U+FFFD`. Foi a causa raiz de "SOCOCO" virar "SOC�CO" no banco e a IA "adivinhar" nomes errados tipo "Socaneco" ou até usar `marca='KELLOGG S'` (dado de importação errado, não alucinação).

Quando `_texto_corrompido` detecta corrupção em `gerar_textos_arte_ia`, o fluxo busca uma descrição/marca **íntegras pelo EAN** nas mesmas fontes do cadastro automático (Cosmos → Open Food Facts → Zaffari, nessa ordem) **antes** de deixar a IA reconstruir. Se achar fonte confiável, o **nome fica travado** nela (`fonte_confiavel = True`) — a IA só gera a headline, nunca reescreve o nome de novo (ela já errou mesmo com entrada limpa numa geração).

Nota: o token do Cosmos (`KZSEuMgGjPb8d9gFztQHiw`, hardcoded em `fetch_product_from_cosmos`) está retornando `401 Unauthorized` — Open Food Facts e Zaffari continuam funcionando e cobrem a maioria dos casos.

### Formato de arquivo: WEBP, não PNG

`compor_texto_na_arte` salva em WEBP (`quality=88`), não PNG — para uma foto (não um gráfico com poucas cores), isso dá ~90% de redução de tamanho com qualidade visualmente idêntica, e o app Android já reconverte tudo pra webp no cache local mesmo (evitava um retrabalho). `_arte_url` só reconhece `.webp` — artes antigas em `.png` viram órfãs automaticamente e regeneram sozinhas na próxima consulta (comportamento esperado, não é bug).

### Fila única de geração de arte (protege contra rate limit do Gemini)

Com vários terminais em lojas/clientes diferentes, gerar arte em paralelo (uma thread por request, como era antes) estourava o rate limit do Gemini (429 RESOURCE_EXHAUSTED). Agora existe **uma fila única processada por um único worker** (`_fila_arte`, `_worker_fila_arte`, `_enfileirar_geracao_arte`) — nunca há mais de uma chamada ao Gemini em andamento ao mesmo tempo, custe o que custar em latência sob carga.

- `_enfileirar_geracao_arte(codbar, img_path, aguardar=False, forcar=False)` é o único ponto de entrada. `aguardar=True` bloqueia até o job terminar (usado onde a rota precisa devolver a `arte_url` na resposta); sem isso é fire-and-forget. `forcar=True` ignora a checagem de "arte já existe" (usado pelo botão de regenerar).
- Os 3 pontos que geram arte no sistema passam todos pela mesma fila: o disparo automático em `GET /produto-imagem/<codbar>` (fire-and-forget), o botão "Gerar/Regenerar arte" do admin (`aguardar=True, forcar=True`) e a rota pública `POST /produto-imagem/<codbar>/gerar-arte` usada pelo app (`aguardar=True`). O contrato HTTP de cada uma **não mudou** — só a execução interna passou a ser serializada.
- O worker refaz a consulta do `Produto` por conta própria dentro do seu próprio `app_context()`, em vez de reaproveitar o objeto SQLAlchemy que o request original carregou — evita problemas de sessão entre threads.
- Sem persistência: se o Flask reiniciar com jobs na fila, eles se perdem, mas isso é inofensivo — a próxima consulta em `GET /produto-imagem/<codbar>` detecta que a arte ainda não existe e reenfileira sozinha (mesmo padrão de auto-recuperação que já existia antes da fila).
- Testado com concorrência real (3 gerações disparadas juntas com `gerar_arte_publicitaria` mockado por um `time.sleep`) confirmando que a concorrência máxima observada é sempre 1, e com uma geração real via Gemini (`POST /admin/gerar-arte/<codbar>`) confirmando que o contrato da rota não mudou.
- Visibilidade: `GET /admin/status-sistema` retorna `fila_arte.pendentes` e `fila_arte.em_processamento`, mostrado ao vivo (poll a cada 5s) num pequeno painel no topo da aba Consulta Rápida.

### Consumo do Gemini (visibilidade, já que o console do Google não é prático pro dia a dia)

Cada chamada real ao Gemini (`gerar_arte_publicitaria` — modelo de imagem — e `gerar_textos_arte_ia` — modelo de texto) é contabilizada via `_registrar_uso_gemini(categoria, sucesso, rate_limited)`, separando sucesso / bloqueio por limite de taxa (429/RESOURCE_EXHAUSTED, detectado pela string do erro) / outro erro, para cada categoria ('imagem'/'texto'). `_status_gemini()` lê esses contadores; aparecem tanto em `GET /admin/status-sistema` (ao vivo) quanto no resumo diário por e-mail/WhatsApp — resetados a cada resumo enviado com sucesso, igual aos contadores do Cosmos (reportam "desde o último resumo", não total histórico).

**Resolução**: a foto crua (produto pequeno, lado a lado com texto) é cacheada a até 512px — ok pra thumbnail. A ARTE (vira fundo de tela cheia no app) precisa de resolução bem maior; isso é responsabilidade do **app Android** (`PriceQueryEngine.downloadProductImageIfNeeded` usa o maior lado da tela do próprio aparelho como teto, não 512px — ver CLAUDE.md do mplayer).

**Cuidado ao mexer em `downloadProductImageIfNeeded` do lado do app**: a foto crua e a arte do mesmo EAN não podem dividir o mesmo nome de cache (`{ean}.webp`) — já causou um bug onde a arte "roubava" o arquivo da foto crua já baixada. A arte usa a chave `{ean}_arte`.

### Refresh visual "big-tech" (pedido do usuário: "mais moderno... elegante... métodos do Google e grandes bigtechs")

Pedido logo em seguida à reorganização da aba Configurações — dessa vez pro **sistema inteiro**, não só uma aba. Como todas as abas do painel compartilham o mesmo `<style>` (um HTML só, sem framework de componentes), a forma de "modernizar tudo" sem reescrever cada aba individualmente foi elevar o **design system compartilhado** (tokens de cor/sombra, tipografia, botões, toggles, cards, tabela) — a mudança se propaga sozinha pra toda aba que usa essas mesmas classes, mesmo raciocínio já usado pro tema escuro (CSS custom properties em vez de cor literal espalhada).

- **Tipografia — Inter (Google Fonts)**: `body { font-family: "Inter", -apple-system, ... }`, carregada via `<link>` com `font-display:swap` — nunca bloqueia o primeiro render, cai pro stack de fontes de sistema se a rede cair (o painel é tipicamente acessado via rede LOCAL da loja, que pode estar de pé mesmo com a internet fora). Inter é a fonte de fato-padrão de praticamente todo painel SaaS moderno (Linear, Vercel, Stripe, Notion, GitHub) — escolha direta pro pedido "métodos de grandes bigtechs".
- **Escala de elevação** (`--shadow-sm`/`--shadow-md`/`--shadow-lg`, + `--radius-sm` e `--ease` pra timing de transição consistente): substituiu o `--shadow` único e achatado que todo card usava — `.card` agora usa `--shadow-md` (mais profundidade que antes), dando uma separação visual mais clara do fundo. Tokens redefinidos no bloco `html[data-theme="dark"]` com opacidade maior (sombra em tema escuro precisa ser mais forte pra ficar visível contra um fundo já escuro).
- **Frosted glass no topbar** (`backdrop-filter: blur(14px) saturate(180%)` + fundo semi-transparente via `color-mix()`): o header fixo deixa de ser um bloco opaco chapado e passa a desfocar sutilmente o conteúdo passando por baixo ao rolar — mesmo efeito usado no macOS/iOS, Material You e a esmagadora maioria de app moderno com header fixo.
- **Botões com glow colorido no hover** (`.btn-primary`): sombra sutil na cor do próprio accent (via `color-mix(in srgb, var(--accent) ..., transparent)`, não um cinza genérico) + leve elevação (`translateY(-1px)`) no hover — o tipo de detalhe que faz um botão de CTA parecer "caro" em vez de completamente plano; mesmo padrão em `.btn-danger`/`.btn-success`.
- **Toggles com glow quando ativos**: `box-shadow: 0 0 0 4px color-mix(...)` ao redor do switch ligado (verde), easing mais suave (`var(--ease)`, uma curva cubic-bezier em vez do linear padrão do navegador) — mesmo tipo de polimento de microinteração usado em switches iOS/Material.
- **Cards de produto (grid da Consulta Rápida) com hover-lift**: `transform: translateY(-2px)` + sombra `--shadow-md` + borda tingida de accent no hover — como esses cards são genuinamente clicáveis (abrem o painel de detalhes), o hover agora comunica isso visualmente, coisa que antes não existia (cards estáticos sem nenhum feedback ao passar o mouse).
- **Tabela**: hover de linha trocado de `var(--bg)` pra `var(--hover)` (o token que já existe especificamente pra isso — `--bg` é pro fundo da PÁGINA fora dos cards, `--hover` é o tom certo pra hover dentro de um card branco/escuro), mais padding nas células, transição suave.
- **Polimento global**: `::selection` na cor do accent, anel de foco consistente (`:focus-visible`) em toda a página (acessibilidade + visual — produtos "big tech" sempre têm um anel de foco nítido), scrollbar fina customizada (Webkit/Blink; navegadores sem suporte só mantêm a barra padrão, sem quebrar nada).

**Risco avaliado e aceito conscientemente**: `color-mix()` e `backdrop-filter` são CSS relativamente recente — funcionam em qualquer navegador atual (confirmado ao vivo, `getComputedStyle` mostrando os valores resolvidos corretamente), mas um navegador MUITO antigo simplesmente ignoraria essas regras específicas (degradação graciosa — sem `color-mix`, a sombra/glow cai pra transparente/nada, sem quebrar layout; sem `backdrop-filter`, o topbar perde o desfoque mas continua funcional, só menos "glass"). Aceitável pro público real deste painel (funcionários acessando de navegador/celular normal, não o terminal Android nativo — que não usa esse HTML de jeito nenhum).

Testado visualmente nos temas claro E escuro (alternando `#btn-theme-toggle` ao vivo), conferido via `getComputedStyle` que `font-family`/`box-shadow`/`backdrop-filter` resolvem pros valores esperados, sem nenhum erro novo de CSS/JS no console (só o erro já documentado e esperado de registro do service worker, sem relação com esta mudança).

**Segunda rodada, com referência visual do usuário** (link do Pinterest — um dashboard estilo "Good morning" com cards de métrica coloridos, mais outros pins próximos de glassmorphism/floating cards, todos em tema escuro): a página exigiu login pra ver os detalhes (não acessada — não crio conta em nada só pra ver uma referência), mas o suficiente já apareceu nas miniaturas pra confirmar a direção. Aplicado especificamente nos **cards de estatística** (`.stat-tile`, aba Estatísticas — 4 cards: total/com foto/sem foto/marcas):
- Barra de destaque colorida de 3px no topo de cada card (`::before`), cor vindo de uma única custom property `--tone` definida inline por instância (`style="--tone: var(--accent)"` etc.) em vez de repetir a cor em dois lugares (antes: só o número tinha `color:` inline, o card em si era neutro).

### Regressão real na produção: cards de Quarentena/Consulta Rápida (grade) sumiam — miniatura e botões invisíveis

Achada pelo usuário direto na VPS em produção, com print — a aba Quarentena (64 registros pendentes acumulados lá) mostrava cards vazios: badge "Pendente" + EAN, sem miniatura nenhuma, sem os botões "Confirmar"/"Liberar" visíveis. Investigado a fundo em vez de assumir — o bug tinha DUAS causas em cadeia, as duas introduzidas pelo próprio refresh visual desta sessão (seção acima):

1. **`.produto-card` virou `display:flex;flex-direction:column`** nesta mesma leva (pro hover-lift do card) — e um filho com `aspect-ratio` (`.produto-card-img`/`.quarentena-card-img`, a miniatura) dentro de um container flex column **encolhe pra altura 0 por padrão** (flex-shrink:1 implícito, sem nenhum conteúdo garantindo um tamanho mínimo) — o `aspect-ratio:1/1` nunca chegava a ser respeitado. Confirmado ao vivo via `getComputedStyle`: `height` da miniatura resolvendo pra `"0px"` mesmo com `width` normal. Corrigido com `flex-shrink:0`.
2. **Depois de corrigir (1)**, um segundo bug apareceu: o CARD INTEIRO colapsava pra ~16px de altura com `overflow:hidden` cortando tudo. **Diagnóstico ERRADO na primeira tentativa, registrado aqui pra não repetir**: achei que era `align-items:stretch` (padrão do Grid) brigando com a altura "auto" da linha, e troquei pra `align-items:start` — isso tirou o CARD do colapso, mas **criou um bug diferente e pior**: os cards passaram a se SOBREPOR uns aos outros (confirmado só depois, com o usuário mandando um segundo print — vários cards com o mesmíssimo `top` em `getBoundingClientRect()`, cada um "vazando" por cima do card da linha seguinte). Só aí a causa raiz real apareceu: pela especificação de CSS Sizing, um elemento com `overflow` diferente de `visible` tem sua contribuição de tamanho MÍNIMO tratada como **~0** em cálculos de layout intrínseco (é assim que `overflow:hidden` corta conteúdo sem forçar o pai a crescer) — e `.produto-card` **é o item do CSS Grid**, então o Grid calculava a altura de cada linha (`grid-auto-rows:auto`) baseado nesse "quase zero", não na altura real (~317px) do card. `align-items` (seja `start` ou `stretch`) nunca foi a causa — só mudava COMO o sintoma aparecia (colapsado vs. sobreposto). Correção de verdade: **removido `overflow:hidden` de `.produto-card`** (o item do grid em si) — o Grid volta a medir a altura real do conteúdo. O recorte visual que dependia desse `overflow:hidden` (cantos arredondados no topo da miniatura) foi movido pra dentro de `.produto-card-img`/`.quarentena-card-img` (`border-radius` só nos dois cantos de cima + `overflow:hidden` PRÓPRIO — como essas têm `height:140px` explícito, não sofrem do mesmo problema: só elementos com altura *implícita*/auto contribuem "zero" quando têm overflow:hidden). `align-items:start` foi revertido pro padrão (`stretch`) — com a causa raiz corrigida, `stretch` dá um resultado mais limpo (cards de uma mesma linha com a mesma altura, botões alinhados no rodapé via `margin-top:auto`) do que `start` teria dado (bordas inferiores desalinhadas quando descrições têm tamanhos diferentes).

**Melhoria pedida junto** ("melhorar a forma que aparece"): mesmo com o bug corrigido, a miniatura em `aspect-ratio:1/1` ficava tão alta quanto a coluna era larga — numa fila de revisão com dezenas de itens (64 na VPS), isso deixava cada card gigante e exigia MUITO scroll pra rever poucos itens por vez. Trocado `aspect-ratio:1/1` por uma **altura fixa** (`height:140px`, mantendo `object-fit:contain` na imagem — nunca distorce, só letterbox se a proporção não bater) — miniatura sempre no mesmo tamanho compacto, independente da largura da coluna. Afeta os dois grids que usam esse padrão (`.produto-card-img` da Consulta Rápida, `.quarentena-card-img` da Quarentena) — mesma correção, mesmo motivo.

Testado ao vivo depois da correção completa (duas rodadas, a segunda direto contra os 64 registros reais da VPS depois que o usuário reportou a sobreposição): `getBoundingClientRect()` de cards consecutivos confirmando `top` estritamente crescente entre linhas (nunca mais o mesmo `top` pra cards de linhas diferentes — a marca registrada do bug de sobreposição); "Revelar" clicado de verdade, miniatura desborra corretamente; badge/EAN/descrição/motivo/origem/botões "Confirmar"/"Liberar" todos visíveis e legíveis, cards de uma mesma linha com altura uniforme; grade da Consulta Rápida (mesmo componente `.produto-card`, catálogo real) conferida também, sem regressão — 4 cards da mesma linha com `top`/`height` idênticos entre si.

**Achado operacional de passagem, sinalizado ao usuário, não uma correção de código**: dos 64 registros pendentes na VPS, a maioria tinha `motivo: 'Fonte exige revisão'` (política de fonte, `FONTE_SERPER_REVISAO_OBRIGATORIA`/`FONTE_PRECOMELHOR_REVISAO_OBRIGATORIA`, ver seção "Toggle individual por fonte de imagem" acima) — ou seja, a fila cresceu tanto porque alguém ligou essa flag pro Serper e/ou PreçoMelhor em produção, não porque o classificador de conteúdo está achando problema real em quase tudo. Vale revisar em Configurações → Fontes de Imagem se essas duas flags ainda precisam estar ligadas, ou se a fila só vai continuar crescendo.

### Layout de viewport fixo: abas e tabelas sempre em largura/altura máxima, scroll só dentro da lista

Pedido do usuário: "as tabelas e abas usar sempre a largura máxima da tela e altura também, manter o scroll dentro das tabelas". Duas mudanças distintas, uma simples e uma estrutural:

**Largura**: antes só 3 abas (Consulta Rápida/Histórico/Quarentena) ganhavam a classe `.wide` pra ocupar a tela toda — as outras 8 ficavam travadas em `max-width:1080px` centralizado. `.content` agora é sempre largura total (`max-width` removido de vez, junto com a regra `.content.wide` e o toggle de classe correspondente no JS — ambos viraram código morto). Mais simples que manter a distinção: todas as abas se beneficiam igual, nenhuma razão real pra Configurações/Estatísticas/WhatsApp ficarem mais estreitas que o resto.

**Altura + scroll interno**: essa é a parte estrutural. Antes, a PÁGINA inteira rolava (`body`/`.main` cresciam com o conteúdo) — numa aba com uma tabela de milhares de linhas, isso significa rolar a página inteira só pra ver a próxima linha, e a paginação/filtros no rodapé/topo saem de vista. Convertido pro padrão de app real (Gmail/Linear/Notion): a casca do painel (`.app`/`.main`) trava em `height:100vh` com `overflow:hidden` (a PÁGINA nunca rola — `html,body{overflow:hidden}`), e só regiões específicas ganham `overflow-y:auto` própria:
- `.content` (flex:1, min-height:0) é o scroll **padrão/fallback** — cobre as abas sem uma lista/tabela dominante (Configurações, Estatísticas, WhatsApp, Remover Fundo, Testar API), que continuam se comportando como antes (rolagem normal), só que agora dentro de uma região contida em vez da página toda.
- As 4 abas com uma lista/tabela GRANDE (Consulta Rápida, Histórico, Imagens Pendentes, Quarentena) ganham uma cadeia de flexbox (`#tab-<aba>{height:100%} → .consulta-layout/.consulta-list-col (ou >.card direto, pendentes/quarentena não usam esse wrapper) → #<aba>-list{flex:1;min-height:0;overflow-y:auto}`) — cada nível repassa `flex:1;min-height:0` pro próximo até chegar na LISTA de verdade, que é quem ganha a barra de rolagem. O resultado: cabeçalho da aba, busca/filtros, e a paginação no rodapé ficam sempre visíveis e fixos; só as linhas da tabela/grade rolam por baixo. `min-height:0` é o detalhe que faz o encadeamento funcionar — sem ele, o comportamento padrão do flexbox ("nunca encolher abaixo do tamanho do conteúdo") quebraria a cadeia inteira e a lista simplesmente cresceria a página de novo.
- **`<thead>`/`th` ganhou `position:sticky;top:0`** (efeito colateral bem-vindo, não pedido explicitamente mas óbvio dado o resto): dentro das 4 listas com scroll interno, o cabeçalho da coluna (EAN/Descrição/Marca/...) agora fica "grudado" no topo enquanto as linhas passam por baixo rolando — sem isso, o cabeçalho sumiria de vista exatamente quando mais se precisa dele (rolando pra baixo numa tabela longa). `background` do `th` reforçado pra combinar com o gradiente sutil dos cards em tema escuro (ver seção anterior) — sem isso, o cabeçalho fixo destoaria visivelmente do fundo atrás dele assim que o scroll passasse por baixo.
- JS: o handler de clique dos `.nav-tab` agora decide `display:'flex'` (as 4 abas com tabela) vs `display:'block'` (as demais) em vez de sempre `'block'` — é essa troca que ativa a cadeia de flex acima; nas abas `'block'`, as regras de `flex-direction`/`height:100%` nos seletores por ID simplesmente ficam inertes (só fazem efeito quando `display` é de fato `flex`).
- **Elementos `position:fixed` (detail-panel, modais, toast, lightbox) não são afetados** — posicionamento fixo é sempre relativo ao viewport, independente de qual ancestral tem `overflow:hidden`/`auto`; confirmado que `.consulta-detail-col` (o wrapper `width:0;height:0` do painel de detalhes) continua exatamente 0x0 mesmo virando item de um flex container agora.

Testado: `document.documentElement.scrollHeight > clientHeight` confirmado `false` (página nunca rola) em todas as abas testadas; as 4 listas com scroll interno confirmadas com `overflow-y:auto` e `scrollHeight > clientHeight` (rolam de verdade) quando têm conteúdo suficiente (Consulta Rápida, com ~945 mil produtos, sempre tem); scroll manual (`scrollTop`) testado na Consulta Rápida — cabeçalho da tabela ficou visivelmente fixo enquanto as linhas passavam por baixo, paginação no rodapé nunca saiu de vista. Testado também em viewport mobile emulado (375×812) — mesmo comportamento, sem overflow horizontal na página, tabela larga rola nas duas direções (`overflow-x` já existia, `overflow-y` novo) dentro da própria área, não da página.

### Bug real de contraste em tema escuro: campos sem estilo caindo no controle nativo do navegador

Pedido do usuário, reportando um bug concreto: "temos inputs que está escuro a cor da fonte e o input também" — campo com fundo E texto ambos escuros, ilegível. Investigado e confirmado como bug real, não relato impreciso.

**Causa raiz**: a regra de estilo dos campos de formulário (`input[type="text"], input[type="password"], input[type="number"], select { ... }`) nunca cobriu todos os tipos de campo que o painel realmente usa — `input[type="email"]` (tela de login), `input[type="time"]` (horário do resumo diário) e `<textarea>` (tokens do Cosmos) ficavam **completamente sem estilo nenhum**, caindo no controle nativo do navegador/SO. Sem uma declaração `color-scheme` na página, o navegador decide sozinho (baseado na preferência do SISTEMA OPERACIONAL, não no tema escolhido AQUI dentro do painel) que paleta usar nesses controles nativos — os dois são independentes, e quando divergem (SO num modo, painel no tema oposto, ou o navegador aplicando um meio-termo inconsistente) o resultado pode ser exatamente fundo e texto ambos escuros.

**Correção, duas partes**:
1. **`color-scheme: light` (em `:root`) / `color-scheme: dark` (em `html[data-theme="dark"]`)** — declaração nova, diz explicitamente pro navegador qual paleta usar em TUDO que ele mesmo desenha (não o CSS da página): popup de `<select>`, spinner de `number`/`time`/`date`, destaque de autofill, scrollbar nativa em navegadores sem suporte a `::-webkit-scrollbar`. Muda dinamicamente junto com o toggle de tema existente (`data-theme`), sem precisar de nenhuma lógica JS nova.
2. **Seletor de estilo dos campos ampliado** pra cobrir todos os tipos realmente usados no painel (`email`, `time`, `date`, `textarea`, além dos que já tinham) — cada um ganhando `background:var(--card)` + `color:var(--text)` explícitos, iguais aos outros campos. Também adicionado: `option { background/color }` (o popup de `<select>` é elemento próprio, não herda do `<select>` fechado automaticamente em todo navegador) e `::placeholder { color: var(--muted) }` (texto de dica tinha contraste ruim em tema escuro, herdando uma cor pensada pro tema claro).

Testado ao vivo nos dois temas (alternando `#btn-theme-toggle`): tela de login com `input[type="email"]` — placeholder e texto digitado claramente legíveis (antes da correção, esse campo específico é a tela que qualquer usuário vê primeiro, o pior lugar possível pra um bug de contraste); textarea de tokens do Cosmos com texto monoespaçado legível; campo de horário (`type="time"`) com o ícone de relógio e o texto "08:00" ambos com contraste correto; `<select>` (Status do Histórico) e seu `<option>` conferidos via `getComputedStyle` — `backgroundColor`/`color` corretos nos dois temas (`rgb(19,27,46)`/`rgb(229,231,235)` no escuro, `rgb(255,255,255)`/`rgb(15,23,42)` no claro); `document.documentElement.style.colorScheme` confirmado resolvendo pra `"dark"`/`"light"` junto com o toggle.

### PWA: painel instalável no celular ("um pwa top") — manifest + service worker + polimento de tela cheia

Pedido do usuário, mesma leva do item acima. Implementado com uma restrição deliberada: **o service worker NUNCA cacheia o HTML do painel nem chamada de API nenhuma** — só os ícones e o `manifest.json`. Dois motivos, documentados também como comentário no próprio `static/sw.js`:
1. É um painel administrativo com dado em tempo real (estoque, fila de quarentena, status de fontes) — "funciona offline" escondendo uma resposta cacheada e desatualizada enganaria quem usa o painel.
2. O HTML de `/configuracoes` é renderizado no servidor com a chave OpenAI/Gemini **já preenchida no próprio markup** (`value="{{ openai_key_full }}"` no `<input>`) — guardar esse HTML no Cache Storage do navegador manteria uma cópia da chave em disco fora do banco, inclusive depois de trocada/revogada. Melhor nunca cachear essa página.

O único motivo real de ter um service worker aqui é técnico: o Chrome exige um com `fetch` handler funcional como critério de instalabilidade (o botão "Instalar app" na barra de endereço) — sem nenhuma necessidade real de funcionar offline pra esse tipo de ferramenta.

- **`static/manifest.json`**: `name`/`short_name`/`icons`/`theme_color`/`background_color` (tons do tema escuro), `display: "standalone"`, `start_url`/`scope` apontando pro painel. Servido via `/static/manifest.json` direto (Flask já serve `static/` — não precisou de rota dedicada, diferente do service worker).
- **Ícones gerados via PIL** (`static/icons/icon-192.png`, `icon-512.png`, `icon-maskable-512.png`) reaproveitando a fonte Montserrat já usada nas artes publicitárias + o mesmo gradiente do `.brand-mark` do próprio painel (`#6366f1` → `#8b5cf6`) com "MB" em branco — zero dependência nova, script descartável (não comitado, só rodado uma vez pra gerar os PNGs finais que ficam versionados).
- **`GET /sw.js`** (rota dedicada em `app.py`, não `/static/sw.js` direto): o escopo padrão de um service worker é o diretório da URL do próprio script — em `/sw.js` isso dá escopo de site inteiro (`/`) sem precisar do header `Service-Worker-Allowed`; em `/static/sw.js` o escopo ficaria preso a `/static/*`, inútil pra controlar o painel. `send_from_directory('static', 'sw.js', mimetype='text/javascript')` + `Service-Worker-Allowed: /` explícito (redundante com o escopo já correto por padrão, mas documentado sem custo).
- **`<head>`**: `<link rel="manifest">`, `theme-color`, `apple-touch-icon` + `apple-mobile-web-app-*` (suporte ao "Adicionar à Tela de Início" do Safari/iOS, que não tem o fluxo de instalação via `beforeinstallprompt` do Chrome), `viewport-fit=cover` no `<meta viewport>` (necessário pra `env(safe-area-inset-*)` funcionar de verdade em vez de sempre resolver pra 0).
- **Botão "Instalar app"** na barra lateral (escondido por padrão, só aparece quando o navegador dispara `beforeinstallprompt` — não existe em Safari/iOS, onde a instalação é manual via Compartilhar; nesse caso o botão simplesmente nunca aparece, sem quebrar nada).

## Atualização automática via GitHub (polling, não webhook)

Pedido do usuário: "quero que o sistema se atualize quando o github receber um push/commit". `_iniciar_agendador_atualizacao()` (thread daemon, mesmo padrão dos outros agendadores) confere a cada 5 minutos se há commit novo em `origin/<branch atual>` e, se houver, aplica sozinho: `git pull` + reinício do processo via `os.execv(sys.executable, [sys.executable] + sys.argv)`.

**Por que polling, não webhook**: essa máquina (e qualquer outra rodando isso numa loja/rede local) não tem garantia de estar acessível publicamente pra receber a chamada HTTP que o GitHub faria num push — então em vez de "o GitHub me avisa", o sistema "pergunta sozinho de tempos em tempos". Teto de 5 minutos entre um push e o sistema notar, não é instantâneo.

**`_git(*args)`**: helper que centraliza toda chamada ao git (`subprocess.run(['git', *args], cwd=BASE_DIR, encoding='utf-8', errors='replace', ...)`) — usado por `_info_versao_git` e `_verificar_e_aplicar_atualizacao_github`. O `encoding='utf-8'` explícito importa de verdade: sem ele, `text=True` sozinho usa o locale padrão do Windows (não é UTF-8) pra decodificar a saída do git, e uma mensagem de commit com acento virava mojibake (`"árvore"` → `"Ã¡rvore"`) — bug real, pego testando o badge de versão no header (próxima seção).

**Proteção principal contra sobrescrever trabalho local**: só faz `git pull` se não houver mudança em arquivo **rastreado** (`git status --porcelain`, ignorando linhas `??` de arquivo nunca versionado). Passou por uma correção real: a primeira versão tratava QUALQUER linha do `--porcelain` como "sujo", inclusive arquivos soltos nunca rastreados — como esta máquina tem ~12 scripts/screenshots avulsos na raiz (débito antigo, sem relação com o código de verdade), isso deixava o auto-update permanentemente bloqueado aqui, mesmo depois de consertar o `.gitignore`. Corrigido pra só considerar "sujo" mudança em arquivo já rastreado (modificado/deletado/staged) — um arquivo nunca versionado não é risco pra um `git pull` na prática.

**Detecção de "tem atualização" também corrigida**: a primeira versão comparava só `local == remoto` (hash do HEAD local vs. `origin/<branch>`) — bug real pego em teste: quando o LOCAL está à frente do remoto (commit feito aqui, ainda não enviado ao GitHub), os hashes são diferentes mas não há nada pra puxar; a função tentava um pull desnecessário mesmo assim. Corrigido com `git rev-list --count HEAD..origin/<branch>` — só considera "atualização disponível" quando esse número é `> 0` (origin tem commit(s) que local realmente não possui).

**`os.execv` pra reiniciar, testado isoladamente**: confirmado funcionando no Windows com um script de teste que se reinicia sozinho 2x em sequência via `os.execv` antes de terminar — a abordagem funciona tanto rodando `python app.py` quanto no `.exe` compilado pelo PyInstaller (`sys.executable` aponta pro lugar certo nos dois casos, ver seção de packaging), sem precisar de nenhum supervisor externo (NSSM, serviço do Windows) pra "trazer de volta" o processo depois do restart — ele se relança sozinho.

Se o pull for aplicado com sucesso, dispara um aviso por WhatsApp antes de reiniciar (`_notificar_atualizacao_whatsapp`, reaproveita `_enviar_texto_whatsapp` — o mesmo helper genérico que o heartbeat horário usa, extraído dele nesta mesma leva). Controlado por `AUTO_UPDATE_ATIVO` (Config, default `'true'`, sem toggle na UI ainda — só setável direto no banco se precisar desligar).

### RESOLVIDO: `.gitignore` corrompido causava `venv/` (16.6k arquivos!) rastreado por engano

## Histórico de buscas e resumo diário do sistema

Tabela `HistoricoBuscaImagem` — hoje é uma **fila de pendências pura**, não mais um log geral de toda consulta de imagem (ver mudança abaixo). Alimentada tanto pelo terminal (`GET /produto-imagem/<codbar>`, `via='terminal'`) quanto por uma retentativa manual no painel (`POST /admin/buscar-imagem/<codbar>`, `via='admin'`); usada tanto pela aba "Histórico" do painel quanto pela fila de pendências do resumo diário (linhas com `encontrado=False` e `notificado_em=NULL`).

### Registro restrito: só produtos cadastrados + só falhas (pedido do usuário, corrigindo poluição real na fila)

Até esta mudança, `_registrar_busca_imagem` gravava uma linha pra **toda** consulta de imagem feita ao sistema — sucesso ou falha, EAN cadastrado ou não. Isso poluía a fila de pendências ("Não encontrados") com EANs que **não são produtos do nosso catálogo** (ex.: código de barras escaneado errado no terminal, produto de outra loja/rede) — o colaborador via esses EANs na fila mas não tinha nada de fato pra "resolver" ali, já que não é um produto nosso.

`_registrar_busca_imagem(codbar, encontrado, ...)` agora só grava uma linha quando **as três condições** abaixo são verdadeiras — o usuário nomeou cada uma explicitamente depois da primeira versão desta mudança, garantindo que a checagem fosse pela existência real do arquivo, não só por uma inferência sobre como a busca correu:
1. **Temos cadastro**: `Produto.query.filter_by(codbar=codbar).first()` existe — só produtos cadastrados de verdade no nosso catálogo geram pendência.
2. **NÃO temos a imagem do produto na pasta**: checado direto via `find_existing_image(codbar, IMAGES_FOLDER, ALLOWED_EXTENSIONS)` dentro da própria função — não confia só no parâmetro `encontrado` que o chamador passou, confere o arquivo de verdade no disco. Defesa extra: mesmo que um chamador futuro passe `encontrado=False` por engano pra um produto que já tem foto, essa checagem impede a linha de pendência fantasma.
3. `encontrado=False` — sucesso nunca vira pendência (nada a resolver); checado primeiro, como atalho barato antes de tocar banco/disco. Os 4 call sites que passam `encontrado=True` nos casos de sucesso não precisaram mudar — viram um no-op silencioso aqui.

A coluna `encontrado` continua existindo no model (linhas antigas, de antes dessa mudança, têm valores `True` reais — não foram apagadas nem alteradas) mas toda linha nova é sempre `False`. O impacto prático: a aba Histórico com filtro "Todos"/"Encontrados" para de ganhar linhas novas a partir de agora (só mostra o histórico antigo já existente) — só o filtro "Não encontrados" (a fila de pendências de verdade) continua recebendo dados novos, e agora só com produtos reais do catálogo que genuinamente não têm foto no disco.

Testado direto (`_registrar_busca_imagem`, sem passar pela rota HTTP, com um EAN de teste isolado criado/removido na hora — sem tocar em nenhum produto real desta vez, ver erro abaixo): (1) sem `Produto` cadastrado, `encontrado=False` → nenhuma linha; (2) com `Produto` cadastrado e SEM imagem no disco, `encontrado=False` → linha criada; o mesmo EAN com `encontrado=True` → nenhuma linha nova; (3) com `Produto` cadastrado e uma imagem de teste realmente salva em `IMAGES_FOLDER`, chamando com `encontrado=False` mesmo assim → nenhuma linha (a checagem de disco pega esse caso, confirmando a defesa extra do item 2 acima).

**Erro cometido testando a 1ª versão desta mudança, documentado aqui pra não repetir**: ao limpar uma linha de teste criada pro EAN real (`7896079480217`), usei `HistoricoBuscaImagem.query.filter(id > 184).delete()` assumindo (errado) que `184` era um limite seguro "antes desta sessão" — na verdade esse número veio de um id de exemplo de um EAN completamente diferente, visto bem antes nesta mesma sessão, e não tinha relação nenhuma com os ids reais das linhas desse produto. Isso apagou **3 linhas de histórico legítimas e antigas** desse produto (de tentativas reais passadas), além da linha de teste — perda real de dado histórico (não do produto, nem da imagem, só de registros de tentativas de busca antigas). Lição, já aplicada no reteste acima: nunca filtrar/apagar dado real por um id numérico "lembrado" — sempre testar com um EAN totalmente isolado/descartável (criado e removido na própria sessão de teste) quando o teste precisar tocar o banco.

### Filtro de Período na aba Histórico, padrão "últimas 24h" (pedido do usuário)

Pedido direto: "adicionar filtros que vai iniciar nas últimas 24h". Antes, a aba Histórico sempre carregava sem nenhum corte de tempo (o filtro "Status" — Todos/Não encontrados/Encontrados — já existia, mas nada limitava POR QUANDO). Numa tabela que só cresce (191 linhas já só neste ambiente de dev), abrir a aba e carregar tudo de uma vez é desnecessário na maioria das vezes — o caso de uso comum é "o que aconteceu recentemente", não o histórico inteiro.

- **Novo select "Período"** (`#historico-periodo`, entre Status e o botão Filtrar): `Últimas 24h` (padrão, `value="24h"`), `Últimos 7 dias` (`7d`), `Últimos 30 dias` (`30d`), `Tudo` (`todos`) — mesmo padrão visual/comportamental dos outros dois filtros (`change` dispara `loadHistorico(1)` de novo, sem precisar clicar em "Filtrar").
- **Backend** (`GET /admin/historico-buscas`): novo param `periodo`, default `'24h'` (o endpoint já teria esse comportamento mesmo se o frontend não mandasse nada — reforça o "padrão 24h" no nível certo, não só na UI). Convertido num corte de data (`datetime.utcnow() - timedelta(hours=...)`) e aplicado como `WHERE criado_em >= desde` — nos DOIS modos do endpoint: no log bruto (`status=todos/encontrado`) filtra as linhas diretamente; no modo agrupado (`status=nao_encontrado/sem_imagem`, ver seção abaixo) filtra as TENTATIVAS individuais **antes** de agrupar — ou seja, "últimas 24h" limita quais tentativas contam pro `tentativas`/`ultima_tentativa` de cada EAN, não um corte por cima do resultado já agrupado. `periodo=todos` (ou qualquer valor não reconhecido) não aplica corte nenhum — mesmo comportamento de sempre.
- Testado direto contra dado real deste ambiente: `periodo=24h` → 0 registros, `periodo=7d` → 18, `periodo=todos` → 191 (progressão consistente, confirma que o filtro está de fato reduzindo o conjunto, não só decorativo); requisição de rede conferida (`read_network_requests`) mostrando o param `periodo` realmente sendo enviado a cada troca; sem overflow horizontal em mobile (375px) com os 3 filtros + botão quebrando linha via `flex-wrap:wrap` já existente.

### Aba "Histórico" → filtro "Não encontrados": agrupado por EAN + ações inline (resolução rápida)

Problema real identificado numa sessão de UX com o usuário: a aba só listava, sem nenhuma ação — pra resolver uma imagem faltante, o colaborador precisava sair da aba, ir em Consulta Rápida, redigitar o EAN, abrir o painel de detalhes, clicar "Buscar imagem". E a lista não agrupava: um produto consultado sem sucesso em N terminais virava N linhas idênticas, sem noção de prioridade.

`GET /admin/historico-buscas?status=nao_encontrado` agora retorna um formato **diferente** dos outros dois filtros (`agrupado: true` no JSON, o frontend usa isso pra saber qual template de tabela renderizar):
- **Agrupado por `codbar`** (`GROUP BY` + `COUNT(*)` como `tentativas`, `MAX(criado_em)` como `ultima_tentativa`) — uma linha por produto, não por tentativa.
- **Ordenado por `tentativas` DESC** — o produto mais pedido e ainda sem imagem aparece primeiro (maior impacto/prioridade).
- **Filtra fora quem já tem foto agora** (`find_existing_image` checado na hora, por cima do resultado agrupado): um upload manual feito fora do fluxo de busca (aba Consulta Rápida → "Enviar/Trocar imagem") não gera uma linha `encontrado=True` no histórico — sem esse filtro extra, o produto continuaria aparecendo como "pendente" pra sempre mesmo já resolvido. Os filtros `'encontrado'`/`'todos'` continuam como log bruto de sempre (auditoria), sem agrupar nem esse filtro extra.

Quatro ações por linha, todas reaproveitando rotas/fluxos que já existiam (nada novo no backend além do agrupamento acima, exceto a ação "Copiar EAN" abaixo, que é 100% frontend):
1. **Buscar** → `POST /admin/buscar-imagem/<codbar>` (rota já existente, local→Bing→Google→Zaffari→PreçoMelhor→Rissul) — na resposta 200, remove a linha da lista na hora (`removerLinhaHistorico`, decrementa o contador também) sem precisar recarregar a página; em 404, só reabilita o botão (a linha fica, `tentativas` sobe 1 na próxima consulta).
2. **Google Imagens** → só frontend, sem rota nova: abre `https://www.google.com/search?tbm=isch&q=<descrição + EAN>` numa aba nova. Existe porque a busca da Bing Image Search está morta (410 Gone, ver seção de débito técnico) e a automação (Google/Zaffari) às vezes não acha — dá pro colaborador fazer a mesma busca manual que faria de qualquer jeito, sem digitar nada.
3. **Copiar EAN** (pedido do usuário) → botão que copia só o código de barras pra área de transferência, sem a descrição junto — útil pra colar direto numa busca externa (site do fabricante, marketplace, etc.) sem precisar apagar o resto do texto. `copiarTexto(texto)` (helper novo, perto de `escHtml`) tenta `navigator.clipboard.writeText` primeiro, mas cai num fallback via `textarea` temporário + `document.execCommand('copy')` se a Clipboard API não estiver disponível — **importante nesse painel especificamente** porque `navigator.clipboard` só funciona em contexto seguro (https ou `localhost`), e esse painel é tipicamente acessado pela rede local via IP puro em HTTP (`http://192.168.x.x:5050`, ver seção "srv-mupa é uma máquina diferente"), onde a API real não existe. Feedback via `toast()` (sucesso ou erro).
4. **Enviar imagem** → `POST /upload-imagem-produto/<codbar>` (rota já existente) via um `<input type="file" accept="image/*">` oculto por linha, disparado pelo clique do botão — mesmo padrão de resolução instantânea da linha no sucesso.

Testado de ponta a ponta num navegador real: os 178 registros brutos do histórico colapsaram pra 3 produtos únicos pendentes, ordenados corretamente (3x/2x/2x); clique real em "Buscar" gerou o `POST` esperado (confirmado por `read_network_requests`) e tratou a resposta 404 corretamente (botão reabilita, linha permanece); os `<input>` ocultos de upload existem um por linha, com `codbar` certo em cada; "Copiar EAN" testado clicando de verdade (não só lendo o código) — toast "EAN ... copiado" apareceu e o clipboard do sistema operacional foi realmente escrito (via `navigator.clipboard`, que funcionou aqui por `localhost` contar como contexto seguro; o fallback via `execCommand` não foi testado ao vivo mas é o mesmo padrão amplamente usado antes da Clipboard API existir).

### Nova aba "Imagens Pendentes" — igual ao Histórico → Não encontrados, mas sem exigir cadastro

Pedido do usuário: uma página dedicada listando **qualquer EAN sem imagem na pasta**, mesmo sem estar cadastrado no catálogo (`Produto`) — diferente da aba Histórico → "Não encontrados", que é deliberadamente restrita a produtos cadastrados (ver seção "Registro restrito" acima). Mesma exibição (produto/tentativas/última tentativa) e as mesmas 4 ações (Buscar / Google Imagens / Copiar EAN / Enviar imagem); sai da lista sozinha assim que uma imagem existir de verdade em `IMAGES_FOLDER` pra aquele EAN.

**Mudança na gravação (`_registrar_busca_imagem`)**: a condição "1. Temos cadastro" foi removida — agora só exige (a) `find_existing_image` confirmando que não há imagem em disco e (b) `encontrado=False`. Isso reverte, na escrita, a restrição adicionada numa leva anterior desta sessão — mas o efeito prático da restrição original (a aba Histórico não "poluir" com EAN que nem é produto nosso) foi preservado, só que **movido pra hora da consulta**: `GET /admin/historico-buscas?status=nao_encontrado` agora filtra explicitamente `HistoricoBuscaImagem.codbar IN (SELECT codbar FROM produto)` — só essa aba continua exigindo cadastro, a gravação em si voltou a ser incondicional (qualquer EAN sem imagem e sem sucesso gera linha).

**Novo valor de `status`**: `GET /admin/historico-buscas?status=sem_imagem` — mesma consulta agrupada de `nao_encontrado`, só que **sem** o filtro de cadastro. Resposta ganhou o campo `cadastrado: bool` por registro (existe `Produto` pra esse EAN ou não) — usado no frontend pra mostrar um badge "sem cadastro" quando aplicável. Os dois modos (`nao_encontrado` e `sem_imagem`) compartilham a mesma fonte de dados (`HistoricoBuscaImagem`) e a mesma lógica de "tira quem já tem foto agora" — só a exigência de cadastro diverge entre eles.

**`admin_buscar_imagem` (ação "Buscar") deixou de 404 quando o EAN não tem `Produto`** — antes rejeitava de cara ("Produto não encontrado"), o que quebraria essa ação pra qualquer item sem cadastro mostrado na nova página. Agora cria um `Produto` mínimo (só `codbar`) na hora, mesmo padrão já usado em `deletar_imagem_produto`/`_quarentenar_imagem`, e segue a busca normalmente.

**Frontend**: nova aba `#tab-pendentes` (entre Histórico e Quarentena na barra lateral), card único (sem coluna de detalhes própria — o painel de detalhes `#hist-detail-panel`/`openHistDetailPanel` já é um overlay `position:fixed`, reaproveitado de qualquer aba sem precisar de layout de duas colunas). As ações de linha (Buscar/Google/Copiar EAN/Enviar imagem) e a remoção da linha ao resolver foram generalizadas pra funcionar nas duas abas: `removerLinhaDeLista(containerId, badgeId, codbar)` substitui a função específica de antes, com `removerLinhaHistorico`/`removerLinhaPendente` como wrappers finos; `handleAcoesRapidasImagem`/`handleUploadRapidoImagem` (antes inline nos listeners do Histórico) viraram funções compartilhadas parametrizadas pela função de remoção certa, ligadas duas vezes (uma por container). O painel de detalhes é literalmente o mesmo (`openHistDetailPanel`) — como ele pode ser aberto a partir de qualquer uma das duas abas, suas 3 chamadas internas de "resolvido com sucesso" viraram `removerLinhaEmTodasAsListas(ean)` (tenta remover a linha das duas listas; a que não tiver essa linha é um no-op silencioso).

Testado de ponta a ponta com EAN descartável (script isolado, sem tocar produto real): EAN sem `Produto` cadastrado, sem imagem, com uma tentativa falha registrada — apareceu em `status=sem_imagem` com `cadastrado: false`, **não apareceu** em `status=nao_encontrado` (Histórico continua íntegro); depois de simular o upload da imagem, sumiu de `sem_imagem` (confirma a condição "só quando não tem imagem na pasta"). Ação "Buscar" testada direto pra um EAN nunca cadastrado — confirmado que não dá mais 404 por falta de cadastro (dá 404 só por não achar em nenhuma fonte, resultado esperado pra um EAN fictício). Testado também visualmente no navegador: aba renderiza, lista carrega (7 pendências reais existentes neste ambiente, incluindo o próprio EAN do incidente `7898909864181` — aparece aqui porque está bloqueado/sem imagem, mesmo comportamento que já tinha na aba Histórico antes desta mudança, não é regressão nova).

**Pedido de esclarecimento numa leva seguinte**: o usuário pediu pra "não registrar se não tiver cadastro" — leitura ambígua o bastante (contradiz diretamente a mudança acima) pra valer perguntar antes de mexer; confirmado que era só reforçar as outras duas condições (checar o arquivo de verdade, olhar sempre pra imagem de produto), não pedir a reversão — comportamento acima mantido como estava.

**Botão "Zerar registros"** (pedido do usuário, mesma leva): `POST /admin/imagens-pendentes/zerar` apaga TODAS as linhas de `HistoricoBuscaImagem` com `encontrado=False` — cadastradas ou não. Como `nao_encontrado` (Histórico) e `sem_imagem` (Imagens Pendentes) são duas VIEWS sobre a mesma tabela, zerar aqui esvazia as duas listas ao mesmo tempo — efeito colateral esperado de um reset completo, não um bug; documentado explicitamente no `confirm()` do botão pra não pegar ninguém de surpresa. Não toca em arquivo, `Produto` nem bloqueio por EAN — só o histórico de tentativas. Testado com um script isolado (linha descartável inserida + zerar + confirma 0 registros restantes).

### Nome "zaffari" suprimido dos rótulos do painel (fonte continua ativa normalmente)

Pedido do usuário, só depois de duas rodadas de esclarecimento (pediu "deletar qualquer descrição Zaffari" — mas `Produto` não tem coluna de fonte, então não tem como saber quais descrições já cadastradas vieram de lá; a intenção real era só cosmética): a palavra "zaffari" não deve aparecer em nenhum rótulo/toast do painel admin, mas a Zaffari **continua sendo usada normalmente** como fonte de imagem e descrição em todos os fluxos — nada foi desativado, nenhum dado foi tocado.

`rotuloFonte(fonte)` (helper no `<script>` de `configuracoes.html`, perto de `escHtml`): retorna a fonte normalmente, exceto quando é `'zaffari'` — aí retorna `null`, e cada chamador trata isso mostrando o texto sem o nome da fonte (ex.: badge "Encontrado" sem o "· zaffari"; toast "Imagem encontrada para X" sem o "via zaffari"). Aplicado nos 3 pontos onde a origem aparece pro usuário: badge da aba Histórico (filtro 'todos'/'encontrado'), toast do botão "Buscar" (filtro 'não encontrados', ver seção acima) e toast de "Cadastrar produto" (Consulta Rápida). Se um dia aparecer um 4º lugar mostrando `origem`/`fonte` de busca de imagem, passar por `rotuloFonte` também, pelo mesmo motivo.

**Resumo diário automático**: `_iniciar_agendador_resumo()` roda uma thread em background (mesmo padrão de `_disparar_geracao_arte_em_background`, sem dependência nova tipo APScheduler) que dispara `enviar_resumo_diario_sistema()` uma vez por dia no horário configurado (`RESUMO_HORARIO`, painel → Configurações → Notificações). Ao contrário de uma versão anterior mais restrita, esse resumo cobre **o sistema inteiro**, não só imagens não encontradas:
- Estatísticas gerais do catálogo (`_estatisticas_gerais`): total de produtos, com/sem foto, com arte publicitária — reaproveita a mesma técnica leve de `/admin/estatisticas` (conta arquivo em pasta, não escaneia produto por produto; o catálogo tem ~945 mil linhas).
- Status da rotação de tokens do Cosmos (`_status_tokens_cosmos`): qual token está em uso, quantos sucessos e quantas rotações por cota esgotada desde o último resumo.
- Cadastros automáticos via fontes externas desde o último resumo (`STATS_CADASTROS_AUTOMATICOS`, incrementado em `register_product_in_database`).
- Imagens de produto ainda não encontradas / não notificadas (o que já existia).

Envia pelos canais ativos:
- **E-mail** (`RESUMO_ATIVO=true` + `RESEND_API_KEY`/`RESUMO_DESTINATARIOS` preenchidos) — via **Resend** (`https://api.resend.com/emails`, chamada HTTP direta com `requests`, sem SDK nem SMTP). `RESEND_REMETENTE` precisa ser de um domínio verificado no Resend; sem configurar, cai no remetente de testes `onboarding@resend.dev` (que só entrega pro próprio e-mail cadastrado na conta Resend — configurar um domínio verificado antes de usar em produção). Testado de ponta a ponta com `requests.post` mockado (monkeypatch) — payload (from/to/subject/html/text), header de autenticação e o tratamento de erro HTTP (ex.: API key inválida) verificados manualmente, sem erros.
- **WhatsApp** (`WHATSAPP_ATIVO=true` + campos preenchidos) — via Z-API ou Evolution API (gateways self-hosted comuns no Brasil), mensagem mais curta (só números-chave, sem a tabela detalhada do e-mail). **Formato do payload ainda não testado contra uma conta real** (`_enviar_whatsapp_resumo_diario`) — se o provedor específico usar um contrato diferente do genérico implementado, ajustar ali.

Diferença importante de comportamento: o resumo agora **sempre envia** quando algum canal está ativo, mesmo sem nenhuma imagem pendente — porque as estatísticas gerais por si só já são um "heartbeat" diário útil. Os contadores (`STATS_COSMOS_SUCESSOS`, `STATS_COSMOS_ROTACOES`, `STATS_CADASTROS_AUTOMATICOS`) são zerados só depois de um envio **bem-sucedido** em pelo menos um canal — cada resumo reporta "desde o último resumo", não o total histórico acumulado. Mesma lógica pras linhas de `HistoricoBuscaImagem` (`notificado_em` só é preenchido em caso de sucesso). Botão "Enviar resumo agora (teste)" no painel dispara manualmente, sem esperar o horário agendado.

## Painel de detalhes e cadastro como popups (não mais inline empurrando o layout)

Pedido do usuário: melhorar a abertura dos detalhes do produto (Consulta Rápida e Histórico) pra abrir como um **popup deslizante na lateral direita**, e o formulário de cadastro pra abrir como um **popup centralizado na tela**, em vez do comportamento anterior (painel de detalhes ocupando uma coluna fixa ao lado da lista o tempo todo — `.consulta-layout { display:flex }` — e o formulário de cadastro sendo um card inline que aparecia empurrando a lista pra baixo).

- **`.detail-panel`** (classe compartilhada por `#detail-panel` da Consulta Rápida e `#hist-detail-panel` do Histórico) virou `position: fixed; top:0; right:0; bottom:0; width:440px; max-width:92vw`, com `transform: translateX(100%)` por padrão e `transition` — a classe `.open` (adicionada por `openDetailModal`/`openHistDetailPanel`, removida por `closeDetailModal`/`closeHistDetailPanel`) desliza o painel pra dentro da tela. `.consulta-layout`/`.consulta-list-col`/`.consulta-detail-col` deixaram de ser um flex de duas colunas — a lista agora ocupa 100% da largura (o painel de detalhes é um overlay, não mais uma coluna reservada o tempo todo).
- **Backdrop** (`#detail-panel-backdrop`/`#hist-detail-panel-backdrop`, `.detail-panel-backdrop`): `position:fixed; inset:0`, escurece o resto da tela enquanto o painel está aberto; clique no backdrop fecha o painel (mesmo handler do botão "×"). Tecla **Esc** também fecha (listener em `document`, só age se o painel em questão estiver com a classe `.open`).
- **`#cadastro-modal-overlay`/`.modal-overlay`**: mesmo padrão de overlay com backdrop, mas com `display:flex; align-items:center; justify-content:center` — o card `#form-cadastro-cosmos` (`.modal-panel`, `max-width:480px; max-height:90vh; overflow-y:auto`) fica centralizado na tela em vez de deslizar de um lado. `abrirModalCadastro()`/`fecharModalCadastro()` (novas funções, substituem o toggle de `style.display` que existia antes) controlam a classe `.show`; clique no backdrop e Esc também fecham, mesmo padrão dos painéis de detalhe.
- **Fecha sozinho ao cadastrar com sucesso**: antes o formulário ficava aberto depois de um cadastro bem-sucedido (só um alerta verde inline avisava); como agora é um popup modal, mantê-lo aberto depois do sucesso é mais ruído que ajuda — `cadastrarProdutoViaCosmos`/`cadastrarProdutoManual` chamam `fecharModalCadastro()` no caminho de sucesso (o `toast()` que já existia continua confirmando a ação). O `showAlert('alert-cadastro-cosmos', ...)` de sucesso foi removido por ficar redundante com o toast + fechamento automático; o de erro continua (mantém o popup aberto pro usuário corrigir e tentar de novo).

- Testado em navegador real, desktop e emulação mobile (375px): painel de detalhes desliza corretamente da direita nas duas abas (Consulta Rápida e Histórico), respeita `max-width:92vw` em telas estreitas (confirmado via `getBoundingClientRect`, painel com 345px de largura a 375px de viewport) sem gerar overflow horizontal na página (`scrollWidth === innerWidth`); popup de cadastro abre centralizado nos dois tamanhos de tela; fluxo completo de cadastro manual (abrir popup → preencher EAN+descrição → cadastrar → popup fecha sozinho) testado de ponta a ponta via HTTP real, produto de teste removido depois.

## Cadastro manual de produto via fontes externas

Três formas de cadastrar um produto que não está no catálogo local, todas na aba "Consulta Rápida":

1. **Botão "+ Cadastrar produto"** (sempre visível, ao lado da busca do catálogo) — abre um formulário dedicado que pede só o EAN e busca **exclusivamente no Cosmos** (`POST /admin/cadastrar-produto-cosmos/<codbar>`, com a rotação de tokens de `fetch_product_from_cosmos`). Se o EAN já existir localmente, avisa e não duplica. Se não achar no Cosmos, retorna 404 sem tentar outras fontes — é um fluxo deliberadamente restrito ao Cosmos, pedido explicitamente pelo usuário.
2. **Botão no estado vazio da busca** — quando a busca por um EAN (8 a 14 dígitos) no catálogo local não encontra nada, aparece um botão que chama `GET /produto/<codbar>` — a mesma rota que já fazia cadastro automático multi-fonte em outros pontos do sistema (Cosmos → Open Food Facts → Zaffari, nessa ordem). Esse é o caminho "genérico", mantido como estava.
3. **"Cadastrar manualmente"** (mesmo formulário do item 1, botão ao lado do "Buscar no Cosmos e cadastrar") — `POST /admin/cadastrar-produto-manual/<codbar>`, pedido do usuário pro caso em que NENHUMA fonte externa (Cosmos, OFF, Zaffari, Google, PreçoMelhor) tem o produto (item novo/exclusivo da loja, sem GTIN público cadastrado em lugar nenhum). Não consulta fonte externa nenhuma — só valida o EAN (`\d{8,14}`, mesma regra do resto do painel) e cria a linha no banco. Idempotente do mesmo jeito que os outros dois: se o EAN já existir, avisa e não duplica, sem sobrescrever o que já tinha.
   - **Descrição e imagem opcionais, na mesma requisição** (form-data: `description` + `file`) — pedido do usuário depois de ver a 1ª versão (só EAN): os campos "Descrição" e "Imagem" do formulário só valem pra esse botão (o Cosmos ignora os dois, já que ele traz os próprios dados). A imagem, se enviada, passa pelo mesmo `IMAGES_FOLDER`/`allowed_file` do upload genérico — sem passar por `save_image_from_response` (não precisa de remoção de fundo nem de baixar de URL externa, já é um arquivo local).
   - **Ainda sem tela de edição de nome/marca depois do cadastro** — se a descrição não for preenchida na hora, o único jeito de completá-la depois é reeditar via banco/CSV; o painel não tem uma tela de edição pós-cadastro (só o upload de foto, `Enviar/Trocar imagem`, continua disponível a qualquer momento no painel de detalhes).

A imagem (thumbnail) que a fonte externa retorna já é baixada e salva automaticamente no fluxo 1 e 2 (`register_product_in_database` + o bloco que salva `dados.get('thumbnail')`); no fluxo 3 a imagem (quando enviada) vem do próprio formulário, não de fonte externa nenhuma.

Testado de ponta a ponta via HTTP real: EAN novo com descrição+imagem cria a linha com os dois preenchidos e `tem_foto=True` (ver seção "Produtos com foto sempre primeiro" abaixo); EAN novo sem nenhum dos dois cria a linha vazia como antes; repetir o mesmo EAN avisa "já cadastrado" sem duplicar; EAN inválido (poucos dígitos) é rejeitado com 400 antes de tocar o banco.

### Produtos com foto sempre primeiro na Consulta Rápida (`Produto.tem_foto`)

Pedido do usuário: a listagem/grade da Consulta Rápida deve mostrar produtos **com foto crua primeiro**, antes dos ~945 mil sem foto. O catálogo é grande demais pra checar o disco (`find_existing_image`) por linha numa ordenação SQL — precisa de uma coluna indexada no próprio banco.

- **`Produto.tem_foto`** (booleana, indexada, `default=False`) — nova coluna, migration `809d6d739559_add_tem_foto_to_produto.py` (Flask-Migrate/Alembic, já configurado no projeto). **O autogenerate do Alembic sugeriu bem mais que a coluna nova** — queria também "corrigir" TEXT→String(255) em toda a tabela (ruído, SQLite não distingue os dois) e **dropar 3 índices existentes** (`ix_produto_cat`/`ix_produto_desc`/`ix_produto_marca`, criados fora do model Python) que não tinham nada a ver com essa mudança — a migration foi reescrita à mão, só com o `add_column`/`create_index` da coluna nova, exatamente pra não perder esses 3 índices por engano. `server_default=sa.false()` no `add_column` é o que permite `NOT NULL` funcionar direto numa tabela com ~945 mil linhas já existentes (cada uma recebe `False` na hora da migração, sem precisar de um passo de backfill separado pra isso funcionar — o backfill que teve que rodar depois foi só pra marcar `True` quem já tinha foto, ver abaixo).
- **`_marcar_tem_foto(produto_ou_codbar, valor)`**: helper central — chamado em TODO ponto que salva ou apaga a foto crua de um produto, pra essa coluna nunca ficar dessincronizada do disco de novo (era exatamente esse o problema do campo legado `foto_png`, que só é atualizado em 1 lugar do código inteiro e por isso é inconfiável). Pontos cobertos: `save_image_from_response` (cobre Bing/Google/Zaffari e o "Buscar com IA" via Gemini, que reaproveitam essa função), `upload_imagem_produto` (Enviar/Trocar imagem), `deletar_imagem_produto` (marca `False` ao excluir), e o cadastro manual (acima). Se um dia aparecer um 4º lugar salvando/removendo arquivo em `IMAGES_FOLDER` direto (sem passar por essas funções), ele também precisa chamar `_marcar_tem_foto`, ou a ordenação volta a ficar errada pros produtos que passarem por ali.
- **Backfill único, feito uma vez nesta sessão**: como a coluna nasce com tudo `False`, um script avulso listou os ~208 arquivos já existentes em `static/imgs_produtos/` e fez `UPDATE ... SET tem_foto=True WHERE codbar IN (...)` em lote (163 bateram com produtos reais do catálogo; o resto são arquivos órfãos de EANs de teste de sessões anteriores, sem produto correspondente). Não precisa rodar de novo — daqui pra frente `_marcar_tem_foto` mantém tudo em sincronia sozinho.
- **`GET /admin/consulta-produtos`**: `ORDER BY` mudou de `description` (ou `(codbar = ?) DESC, description` na busca) pra `tem_foto DESC, description` (`(codbar = ?) DESC, tem_foto DESC, description` na busca — o EAN exatamente pesquisado continua tendo prioridade máxima, mas dentro dos resultados quem tem foto some primeiro).
- **Backup antes de migrar**: `instance/produtos.db` (187MB, ~945 mil linhas) foi copiado pra `instance/produtos.db.bak_pre_tem_foto` antes de rodar `flask db upgrade`, já que um `ALTER TABLE` no SQLite via Alembic (`batch_alter_table`) recria a tabela inteira por baixo — não é destrutivo em condições normais, mas o backup é uma rede de segurança barata pra uma operação que mexe na tabela inteira. Pode ser apagado quando não for mais necessário; não é rastreado pelo git (dentro de `instance/`, no `.gitignore`).

#### Imagens "órfãs" (arquivo sem `Produto`) também aparecem na Consulta Rápida, com botão "Cadastrar"

Achado na VPS (recém migrada, banco copiado do `srv-mupa` mas `static/` ainda não): a ordenação "com foto primeiro" na verdade estava funcionando certinho (é uma coluna do banco, `tem_foto`, não depende do disco) — o que confundiu foi que os produtos com `tem_foto=True` apareciam todos com `foto_png: null` porque o ARQUIVO ainda não tinha chegado na VPS. Não era bug de ordenação — ver seção do incidente/migração pra VPS pra mais contexto.

No meio dessa investigação, o usuário pediu uma coisa nova: até então, um arquivo em `static/imgs_produtos/` sem `Produto` correspondente (já documentado como possível — ver "Backfill único" acima, "arquivos órfãos de EANs de teste") era **completamente invisível** na Consulta Rápida, porque a rota sempre partiu de `SELECT ... FROM produto` — não tem como aparecer algo que não é uma linha dessa tabela.

- **`_listar_imagens_orfas(search='')`**: varre `IMAGES_FOLDER` (não a tabela — o volume de arquivos é sempre muito menor que os ~945 mil produtos, escanear a pasta é barato; o oposto, escanear todo o catálogo procurando quem não tem arquivo, seria caro demais a cada consulta) e devolve os EANs (nome do arquivo) que não batem com nenhum `Produto.codbar`. `search`, quando preenchido, filtra pelo EAN em si — órfão não tem descrição/marca pra buscar por outros campos.
- Órfãos entram **só na página 1** de `GET /admin/consulta-produtos` (não replica a varredura em toda página seguinte — o conjunto é sempre pequeno, cabe inteiro ali), com o `LIMIT` da consulta SQL da página 1 reduzido na mesma proporção (`per_page - len(orfaos)`) pra a página não vir com `per_page + N` itens. Offset das páginas seguintes ajustado pra continuar exatamente de onde a consulta SQL da página 1 parou.
- Cada órfão vem com `'orfao': true` no JSON, `descricao`/`marca`/`categoria`/`preco_medio`/`arte_url` todos `null` (não tem de onde vir esse dado). Frontend (`renderConsultaTableHtml`/`renderConsultaGrid`) desenha essas linhas/cards diferente — fundo destacado (`var(--hover)`), texto "Imagem sem cadastro no catálogo" no lugar da descrição, e um único botão **"Cadastrar"** (`data-action="cadastrar-orfao"`) no lugar das ações normais.
- Botão abre o MESMO popup de cadastro manual de sempre (`abrirModalCadastro`, ver seção "Painel de detalhes e cadastro como popups"), agora aceitando um EAN pra pré-preencher (`abrirModalCadastro(ean)`) — como o EAN já é conhecido (veio do nome do arquivo), o foco vai direto pro campo de descrição em vez do campo de EAN. Cadastro reaproveita `POST /admin/cadastrar-produto-manual/<ean>` sem nenhuma mudança — a imagem já existe em disco, não precisa reenviar nada; assim que o `Produto` é criado, a mesma imagem passa a ser encontrada normalmente por `find_existing_image` e o item some da lista de órfãos na próxima consulta (não é mais órfão, é um produto cadastrado com foto).
- Testado de ponta a ponta com EAN descartável (cópia da imagem de referência salva direto em `IMAGES_FOLDER`, sem passar por `save_image_from_response`, simulando um órfão real): apareceu com `orfao: true` numa busca por EAN; cadastro manual via API confirmou `201`; busca seguinte pelo mesmo EAN voltou sem a chave `orfao` (produto normal, com a descrição cadastrada) — arquivo e `Produto` de teste removidos depois.

### Rotação de tokens do Cosmos (plano free, cota por token)

O Cosmos free tem cota mensal por token. Em vez de um único `COSMOS_API_TOKEN`, o painel agora guarda uma **lista** (`COSMOS_API_TOKENS`, um por linha, textarea em Configurações → "Tokens Cosmos"). `fetch_product_from_cosmos`:
- Começa pelo índice guardado em `COSMOS_TOKEN_INDEX_ATUAL` (não sempre do token #1 — evita re-testar tokens já sabidamente esgotados a cada chamada).
- Se a resposta for **401/402/403/429** (token inválido ou cota esgotada), avança pro próximo token da lista e tenta de novo, até esgotar a lista inteira.
- Se a resposta for **404** (produto não existe no Cosmos — não é problema de token), retorna `None` na hora, sem rotacionar.
- Ao ter sucesso ou esgotar todos os tokens, persiste o índice final em `COSMOS_TOKEN_INDEX_ATUAL` pra próxima chamada já começar dali.
- Contadores `STATS_COSMOS_SUCESSOS` e `STATS_COSMOS_ROTACOES` (Config) acumulam desde o último resumo diário enviado (zerados lá, não aqui) — usados no e-mail/WhatsApp de resumo.

Testado com tokens falsos direto contra a API real do Cosmos (confirma 401 em cada um → rotaciona → esgota → `None`) e com `smtplib`/`requests` mockados via monkeypatch pra validar o caminho de sucesso (token 2 funciona, índice persiste, chamada seguinte já pula direto pro token 2).

**Cuidado, API do Cosmos real é DIFERENTE da assumida inicialmente** — a primeira versão usava `https://api.cosmos.bluesoft.com.br/gtins/<ean>.json` com `Authorization: Bearer <token>` (formato copiado do código antigo/hardcoded já existente no projeto antes desta sessão). Com tokens reais do usuário, isso retornava 401 "Token Inválido" em TODOS os tokens — confirmado com `curl` direto que a causa não era token inválido de verdade, mas **endpoint e header errados**. O formato correto (confirmado pelo usuário rodando um `curl` que funcionou, e replicado com sucesso):
```
GET https://cosmos.bluesoft.com.br/api/gtins/<ean>.json
Header: X-Cosmos-Token: <token>   (não é Authorization: Bearer!)
```
`fetch_product_from_cosmos` já foi corrigido pra usar essa URL/header. Testado com tokens reais após a correção — cadastro via `/admin/cadastrar-produto-cosmos/<ean>` funcionou (retornou produto real, HTTP 201).

## WhatsApp — gestão de instância via Evolution API (aba dedicada)

Nova aba "WhatsApp" no painel faz a gestão completa de uma instância na [Evolution API](https://docs.evolutionfoundation.com.br/evolution-api/installation) (servidor self-hosted) — criar instância, mostrar QR code pra escanear, checar status de conexão, listar todas as instâncias do servidor, desconectar, excluir e testar envio. Reaproveita as mesmas chaves de Config já usadas pelo resumo diário (`WHATSAPP_BASE_URL`, `WHATSAPP_TOKEN`, `WHATSAPP_INSTANCE`, `WHATSAPP_NUMERO_DESTINO`) — criar/conectar uma instância aqui é o que torna o canal WhatsApp do resumo diário funcional.

**Contrato real da Evolution API** (confirmado contra um servidor real do usuário, não documentação genérica assumida):
- `POST /instance/create` — header `apikey`, body `{instanceName, qrcode: true, integration: "WHATSAPP-BAILEYS", number?}`. **Não mandar `token` no body** — se for igual ao apikey global (ou de outra instância já existente), a API rejeita com `"Token already exists"`; deixar a Evolution gerar o hash da instância sozinha. Resposta traz `qrcode.base64` (data URI, pronta pra `<img src>`) e `qrcode.pairingCode`.
- `GET /instance/connect/{instanceName}` — regenera o QR (útil quando o anterior expira antes de escanear). Resposta: `{base64, pairingCode, code}` (sem o wrapper `qrcode.`, direto na raiz — diferente do `/create`).
- `GET /instance/connectionState/{instanceName}` — resposta `{instance: {state}}`, `state` ∈ `open` (conectado) / `close` (desconectado) / `connecting`.
- `GET /instance/fetchInstances` — lista todas as instâncias do servidor (array de `{instance: {instanceName, status, connectionStatus: {state}}}`).
- `DELETE /instance/logout/{instanceName}` — desconecta sem apagar a instância.
- `DELETE /instance/delete/{instanceName}` — apaga a instância.
- `POST /message/sendText/{instanceName}` — body `{number, textMessage: {text}}` — **atenção**: o campo é `textMessage.text` (aninhado), não `text` solto na raiz. Esse era um bug real no código de envio do resumo diário (`_enviar_whatsapp_resumo_diario`) escrito antes de eu confirmar o contrato oficial — já corrigido.

O painel faz polling de `GET /admin/whatsapp/status` a cada 4s enquanto uma instância está configurada, escondendo o QR automaticamente assim que o estado vira `open`. A opção de provedor "Z-API" (genérica, nunca testada) foi removida da UI — o sistema hoje só suporta Evolution API de verdade, com essa página dedicada.

### Heartbeat horário por WhatsApp (07h-22h) — "avisar se o sistema parou"

Pedido explícito do usuário: "o sistema nunca deve parar" + um jeito de perceber quando parar. Um processo que já morreu não consegue avisar sobre si mesmo (não existe hook de "estou caindo" confiável em qualquer falha — crash da JVM/CPython, máquina desligada, processo morto pelo SO), então a estratégia é a mesma de qualquer monitoramento por heartbeat/dead man's switch: mandar uma mensagem previsível a cada hora cheia (XX:00), das 07:00 às 22:00, e deixar a **ausência** de uma mensagem esperada ser o próprio aviso — se não chegou a mensagem das 14h, algo parou entre 13h e 14h.

`_iniciar_agendador_status_horario()` (thread daemon, mesmo padrão de `_iniciar_agendador_resumo`):
- Fora da janela 07-22h, dorme direto até o início do próximo expediente (não acorda de hora em hora à toa de madrugada) — testado com simulação dos horários de borda (00:10, 06:55, 21:45, 22:05) antes de rodar de verdade.
- `try/except` **dentro** do loop, por iteração — uma falha de rede na Evolution API (ou qualquer outro erro) derruba só aquele envio específico, nunca o agendador; "nunca deve parar" vale pro próprio mecanismo de aviso também, não só pro resto do sistema.
- Na primeira execução após o processo subir, se estiver dentro do horário comercial, envia IMEDIATAMENTE com texto diferenciado ("🟢 Sistema iniciado") em vez de esperar a próxima hora cheia — sinal extra e complementar ao heartbeat regular: se o processo cair e alguém (ou um supervisor) reiniciar, essa mensagem fora do padrão avisa que houve um restart.
- Controlado por `STATUS_HORARIO_ATIVO` (Config, default `'true'` — ativo assim que o WhatsApp em si estiver configurado, sem precisar de opt-in extra; adicionado à mesma lista `NOTIFICACAO_CONFIG_KEYS`/rota `save_notificacoes` já usada pelos outros toggles de notificação).
- Mensagem (`_montar_mensagem_status_horario`) é bem mais enxuta que o resumo diário — só fila de arte (pendentes/em processamento), uso do Gemini e status do token Cosmos atual, o suficiente pra confirmar num relance que o sistema está de pé.

Testado enviando de verdade pro número configurado (`_enviar_status_horario_whatsapp` chamada manualmente) — mensagem chegou via Evolution API sem erro. Reaproveita a mesma instância (`bot_imgs`) e número (`WHATSAPP_NUMERO_DESTINO`) já usados pelo resumo diário — não é um canal novo, é o mesmo WhatsApp com uma cadência diferente.

**Limite conhecido, deliberadamente fora de escopo por ora**: isso detecta parada por AUSÊNCIA de mensagem (o usuário percebe, mas só na próxima hora cheia esperada) — não é um alerta ativo e imediato de queda. Um alerta imediato de verdade exigiria um processo INDEPENDENTE (fora deste Flask) fazendo ping periódico e alertando via Evolution API diretamente se o servidor não responder — não implementado ainda porque não foi pedido explicitamente; se o heartbeat horário se mostrar insuficiente na prática, esse é o próximo passo natural.

## Kill switch mestre de Gemini/Vertex AI (`GEMINI_ATIVO`) — desligado a pedido do usuário por causa de custo

Pedido direto do usuário: "quero desativar os custos que vamos ter com o GOOGLE, quero usar sem custo, encontre uma forma" seguido de "Pode desativar tudo que está usando google com custos, valores muito alto". Perguntei explicitamente (`AskUserQuestion`) qual fonte era a do custo alto — resposta confirmada: **Gemini / Vertex AI (Google Cloud)**, não Google Custom Search — e como proceder sabendo que isso também desliga o classificador de conteúdo impróprio/verificação de correspondência (ver seção do incidente do EAN `7898909864181` mais acima) — resposta confirmada: **"Desligar tudo do Gemini mesmo assim"**, aceitando o trade-off conscientemente.

`_gemini_ativo()` (helper novo, ao lado de `_imagem_e_segura`): lê `Config['GEMINI_ATIVO']` (default `'true'`). Toggle em Configurações → Comportamento → "⚠️ Gemini / Vertex AI (Google Cloud) — desliga tudo", mesmo padrão de toggle já usado no resto do painel (`toggle_gemini_ativo`/`data-key="GEMINI_ATIVO"`/`setToggle`).

**Design deliberado: reaproveitar o fallback de "sem chave" que cada função já tinha, não criar um caminho novo.** Toda função que chama o Gemini neste projeto já tinha um `if not api_key: <comportamento seguro>` (fail-open ou erro tratado, dependendo da função — comportamento testado e confiável há várias levas desta sessão). Em vez de inventar um comportamento novo pro caso "desligado", a condição virou `if not api_key or not _gemini_ativo(): <mesmo comportamento de sempre>` nos **8 pontos** que chamam a API do Gemini de fato:
- `_imagem_e_segura` → `True` (fail-open, mesmo default de sempre quando a classificação não pode rodar).
- `_imagem_corresponde_descricao` → `True` (mesmo fail-open).
- `_buscar_imagens_gemini_web` (botão "Buscar com IA") → `([], mensagem explicando que está desativado)`.
- `gerar_termos_sugestao_ia` → `None` (cai pro fallback de busca fuzzy local, mesmo comportamento de "sem chave").
- `gerar_textos_arte_ia` → retorna o nome cru (sem reescrever), sem headline/benefícios — mesmo fallback de sempre.
- `gerar_arte_publicitaria` / `gerar_arte_publicitaria_vertical` → `ValueError` (mesma exceção tratada de sempre pelos call sites).
- `_enfileirar_geracao_arte` (o único ponto de entrada da fila de arte, cobre os 4 gatilhos de geração) → `None` (nem enfileira o job).

**Chave da API NUNCA é apagada** — só para de ser lida/usada. Deliberado: religar o recurso depois vira só marcar o toggle de volta, sem precisar voltar no Google Cloud Console pra recuperar a chave.

**Deliberadamente fora do escopo deste switch** (não são Gemini/Vertex AI, o usuário confirmou que só essa fonte é o problema de custo):
- **Serper** (`buscar_e_salvar_imagem_serper`, `SERPER_API_KEY`) — proxy pago de busca de imagem, provedor totalmente diferente, sem relação com o Google Cloud.
- **Google Custom Search** (`fetch_product_from_google`/`buscar_e_salvar_imagem_google`) — cota gratuita diária, não é Vertex AI.
- **`api_teste_gemini`** (botão manual "Testar Conexão" da chave Gemini em Configurações) — deixado funcional de propósito: é uma ação humana pontual (não uso automático em massa), útil pra confirmar que a chave em si continua válida mesmo com o recurso desligado, antes de religar.

**Efeito prático de desligar**: arte publicitária (nova ou regeneração) para de ser gerada, sugestão de nome/headline cai pro fallback local, "Buscar com IA" fica inerte (mensagem explicando o motivo), e — a parte que exige atenção — o classificador de conteúdo impróprio e a verificação imagem×descrição também ficam inertes (fail-open), ou seja, a proteção criada depois do incidente do EAN `7898909864181` fica temporariamente sem efeito enquanto o switch estiver desligado. Trade-off aceito explicitamente pelo usuário, documentado aqui pra não ser esquecido — religar assim que o custo for resolvido.

Testado de ponta a ponta: toggle via API (`POST /configuracoes` `toggle_gemini_ativo`) liga/desliga e persiste corretamente (`GET /api/config` reflete `gemini_ativo`); os 8 pontos de chamada testados diretamente com `GEMINI_ATIVO=false` e uma chave real configurada (pra isolar que o short-circuit é pelo toggle, não por falta de chave) — todos retornaram exatamente o fallback esperado sem fazer nenhuma chamada real à API; testado também via clique real no toggle do navegador (não só a API) — `toggle-gemini-ativo` muda de classe (`active` ↔ sem classe) e persiste no backend.

## Botão "Marcar como sem imagem" — placeholder genérico fixo pra produto que realmente não tem foto

Pedido do usuário: um botão pra "setar o produto como sem imagem", junto com uma URL específica (`https://www.supratec.com.br/img/p/br-default-large_default.jpg` — um gráfico genérico "IMAGEM INDISPONÍVEL": ícone de câmera cinza + texto, fundo branco) pra "baixar e usar no EAN". Interpretação: em vez de um produto sem foto ficar indefinidamente sem imagem nenhuma (reaparecendo toda hora em Histórico "Não encontrados"/Imagens Pendentes, sujeito a repetidas tentativas automáticas de busca), o botão salva esse gráfico fixo como a foto do produto — uma forma explícita e definitiva de dizer "não tem foto em nenhuma fonte, parem de tentar" sem inventar uma foto real que não existe.

- **`IMAGEM_SEM_FOTO_URL`** (constante) + **`_obter_imagem_sem_foto_placeholder()`**: baixa uma única vez e cacheia em `IMAGEM_SEM_FOTO_CACHE` (`static/sem_imagem_placeholder.jpg`, fora do controle de versão — mesmo padrão de qualquer outro arquivo dentro de `static/`, `.gitignore` já cobre `static/*` — se re-baixa sozinho na primeira vez que rodar em cada ambiente, dev ou VPS) — evita bater no site externo a cada clique, já que é sempre o mesmo arquivo fixo.
- **`POST /admin/marcar-sem-imagem/<codbar>`**: cria um `Produto` mínimo se o EAN ainda não tiver cadastro (mesmo padrão de `admin_buscar_imagem` — necessário pra funcionar também a partir de "Imagens Pendentes", que lista EAN sem cadastro), salva o placeholder em `PROCESSED_IMAGES_FOLDER/<codbar>.png`, marca `tem_foto=True` e limpa qualquer entrada de quarentena ainda pendente do mesmo EAN (`_eliminar_duplicatas_pendentes`, mesmo raciocínio de "EAN resolvido, quarentena antiga virou ruído" já usado em `save_image_from_response`).
- **Deliberadamente NÃO reaproveita `save_image_from_response`**, embora seja o chokepoint de toda outra fonte de imagem — dois motivos concretos: (1) remoção de fundo (rembg) destruiria o próprio gráfico (fundo branco liso é exatamente o tipo de área que o modelo de segmentação recortaria como "fundo", levando o ícone/texto junto ou deixando um resultado quebrado); (2) o classificador de correspondência imagem×descrição (`_imagem_corresponde_descricao`, quando o Gemini estiver ligado) rejeitaria SEMPRE esse placeholder, já que ele nunca "parece" o produto cadastrado — é uma imagem intencionalmente genérica, não uma tentativa de foto real. Como é uma escolha humana deliberada e um arquivo fixo conhecido (não uma busca automática de fonte externa não confiável), salva direto, sem essas duas checagens.
- **Uma vez que existe QUALQUER imagem salva pro EAN, a busca automática nem dispara mais** (mesmo mecanismo de sempre, ver `obter_imagem_produto`) — não foi necessário also usar `Produto.busca_imagem_bloqueada`; o próprio placeholder já impede re-tentativas futuras.
- **Botão em ambos os painéis de detalhe** (Consulta Rápida `#detail-btn-marcar-sem-imagem`, Histórico/Imagens Pendentes `#hist-detail-btn-marcar-sem-imagem`), ao lado de "Enviar/Trocar imagem" — mesmo padrão de toda feature recente que toca os dois painéis simultaneamente. Confirmação (`confirm()`) antes de agir, já que sobrescreve a foto atual se houver uma (mesmo padrão de "Excluir imagem").

Testado de ponta a ponta com EANs descartáveis (criados/removidos na própria sessão de teste, nenhum produto real tocado): chamada direta à rota confirmou `Produto` criado, `tem_foto=True`, arquivo salvo (~32KB PNG) e reuso do cache local na 2ª chamada sem novo download; testado também via clique real no navegador nos dois painéis — Consulta Rápida (produto já cadastrado) e Imagens Pendentes (EAN sem cadastro, só uma tentativa registrada) — confirmando nos dois casos que o painel atualiza a imagem exibida na hora, mostra o toast de sucesso, e (no caso de Imagens Pendentes) a linha some da fila de pendências sozinha, sem precisar recarregar a página.

### "Revelar tudo" + "Marcar como sem imagem" também na Quarentena

Dois pedidos do usuário na sequência, ambos na aba Quarentena:

**"Revelar tudo"** (`#btn-quarentena-revelar-tudo`, ao lado de "Filtrar"): desborra de uma vez todas as miniaturas já carregadas na página atual da grade — útil quando se quer revisar a fila inteira visualmente em vez de clicar "Revelar" card por card. Como essa rota já chama `_eliminar_duplicatas_pendentes(codbar)` internamente (sem exclusão — apaga TODA entrada pendente do mesmo EAN), a própria entrada de quarentena sendo revisada agora já é removida como efeito colateral do backend — não precisou de uma chamada extra tipo `/confirmar` depois (diferente do padrão usado em "Enviar imagem manualmente"/"Buscar com IA" nesse mesmo popup, que chamam `/confirmar` à parte porque a rota de upload/definir-URL não limpa quarentena de outros EANs da mesma forma). Testado confirmando que só a entrada do EAN marcado some (uma 2ª entrada de outro EAN, deixada de propósito no mesmo teste, permaneceu intocada).

Testado de ponta a ponta com 2 EANs descartáveis em quarentena (imagens sintéticas pequenas, criadas/removidas na própria sessão de teste): "Revelar tudo" clicado com 16 entradas pendentes na página — todas as 16 miniaturas (incluindo as 2 de teste) viraram blob `<img>` reais com dimensões corretas, num único clique; "Marcar como sem imagem" testado abrindo o popup de uma das entradas de teste — popup fechou sozinho, contador de pendentes caiu de 16 pra 15, produto passou a ter `foto_png` apontando pro placeholder, e a 2ª entrada de teste (EAN diferente) permaneceu pendente sem ser tocada.

### Contador de "imagens encontradas" por fonte, na própria tabela de Fontes de Imagem

Pedido do usuário: "quero que conte quantas imagens foi encontrada para cada fonte". Nova coluna "Imagens Encontradas" na tabela Configurações → Fontes de Imagem (ao lado de "Ativa"/"Revisão obrigatória"), uma por fonte (Google/Zaffari/PreçoMelhor/Rissul/Sonda/Unidasul/Serper).

- **`_incrementar_contador_fonte(origem)`**: incrementa `Config['FONTE_<NOME>_IMAGENS_ENCONTRADAS']` (string numérica, mesmo padrão de qualquer outro contador do projeto). No-op silencioso se `origem` não estiver em `FONTES_IMAGEM_DISPONIVEIS` (upload manual, "Buscar com IA" via `origem='ia'`, reprocessamento de auditoria — nenhum desses tem linha na tabela, não há onde contar).
- **Chamado de dentro de `save_image_from_response`**, no caminho de SUCESSO (depois de `_marcar_tem_foto`/`_eliminar_duplicatas_pendentes`, logo antes do `return 200`) — o mesmo chokepoint por onde passam as 7 fontes automáticas. Uma imagem que caiu em quarentena (rejeitada por conteúdo impróprio, política de fonte ou descrição incompatível) **não conta** — só incrementa quando a imagem realmente vira a foto do produto.
- **Cumulativo, nunca reseta sozinho** — diferente dos contadores do resumo diário (`STATS_COSMOS_SUCESSOS` etc., que zeram a cada envio bem-sucedido), este é uma métrica histórica "desde sempre", não "desde o último resumo". Não foi pedido nenhum botão de reset, então não tem um.
- Exposto em `fontes_imagem_contagem` nos dois endpoints JSON de configuração (`GET /configuracoes`, `/api/config`), populado no frontend no mesmo loop que já preenche os toggles "Ativa"/"Revisão obrigatória" de cada fonte.

Testado: chamada direta a `save_image_from_response(..., origem='google', ...)` incrementou o contador de 0 pra 1 (dentro de `test_request_context`, já que a função usa `url_for` internamente e não tem contexto de request fora de uma rota HTTP real — mesma particularidade já documentada nesta sessão); `_incrementar_contador_fonte('ia')` confirmado como no-op (não cria nenhuma chave de config pra uma origem fora da tabela); tabela conferida visualmente no navegador com valores semeados manualmente (Google=42, Serper=7) — coluna nova renderiza corretamente ao lado dos toggles existentes. Valores de teste zerados depois, sem deixar contagem fictícia no ambiente.
